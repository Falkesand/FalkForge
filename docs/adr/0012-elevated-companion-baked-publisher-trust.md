# 12. The elevation companion verifies publisher authorship against its own baked key set

- Status: Accepted
- Date: 2026-08-24
- Deciders: Peter Falkesand

## Context

ADR 0011 closed a time-of-check-to-time-of-use gap: the elevated companion
(`FalkForge.Engine.Elevation`, the process that runs as SYSTEM) now opens the MSI itself, holds a
read-share handle across the hash check and the install, and resolves every reparse point before
using the path. That bound the installed bytes to a specific file on disk, so a same-user process
could no longer swap the file underneath the elevated side between check and use.

ADR 0011 said plainly that this was not a full fix, in its "Consequences that are not a full fix"
section:

> The hash the elevated side compares against comes from the engine process, over the same pipe,
> and the engine runs at the same integrity level as the attacker in this threat model. Someone
> who can inject code into the engine process ... can simply send a hash that matches whatever
> file they placed, and the elevated side will verify it successfully and run it anyway. ... It
> does not make the elevated side independently certain of what it is installing: the elevated
> side's only source of truth for "what hash should this be" is still a value the unprivileged,
> same-user engine process sent it.
>
> The durable fix is a trust anchor that does not depend on the engine process's own honesty ...
> plus lifting the existing signed-manifest mechanism ... into `FalkForge.Engine.Protocol` so the
> elevated side can check the hash against a signature it verifies itself, rather than trusting a
> bare value from the wire payload.

This ADR is that follow-up. The unelevated engine already has a baked publisher-key set and a
signed-manifest verification path (ADR 0009's `TrustPolicy`, `PayloadIntegrityGate`, and
`ManifestSignatureEnvelope`, documented in `documentation.html` §23, "Who the Installer Trusts").
Those types lived only in `FalkForge.Engine`, an assembly the elevation companion does not
reference, so the companion had no way to run the same check itself.

## Decision

`FalkForge.Engine.Elevation` gets its own baked publisher-key set, independent of the wire payload,
and verifies the MSI's signed manifest against that set before installing anything.

- **The companion bakes its own trust anchor at build time.** `TrustedKeys.targets` (previously
  imported only by `FalkForge.Engine.csproj`) is now also imported by
  `FalkForge.Engine.Elevation.csproj`. A publisher passes `-p:FalkForgeTrustedKey=<fingerprint>`
  when publishing the companion the same way they already do for the engine, and the target
  generates a `BakedTrustedKeys` type inside the companion binary itself. An empty baked set (the
  property omitted) means the companion trusts no publisher.
- **`TrustPolicy` and `PayloadIntegrityGate` moved into `FalkForge.Engine.Protocol`**, the shared
  assembly both the engine and the companion reference, so the companion can call the same
  verification code the engine already used, instead of a second implementation drifting from the
  first. The move changed only which assembly holds the types; the namespace
  (`FalkForge.Engine.Integrity`) and behavior are unchanged.
- **`MsiInstallCommand.Execute` verifies the manifest before opening the file.**
  `VerifyPublisherAndResolveSignedHash` deserializes the manifest sent over the wire, then calls
  `PayloadIntegrityGate.Verify` against `TrustPolicy.FromBakedKeys(requireSigned: true,
  isUpdatePath: false, storedEpoch: 0)`. `requireSigned: true` means every elevated MSI install
  needs a publisher signature the companion's own baked set trusts. `isUpdatePath: false` is
  deliberate: the companion has no way to read "is this a fresh install or an update" off the wire
  without trusting the same caller this whole change distrusts, so it always applies fresh-install
  semantics. The hash `MsiInstallCommand` binds the file to afterward (the ADR 0011 mechanism) is
  the SIGNED hash this gate resolves from the manifest, never the hash value the caller sent
  alongside the file path (that value is still read off the wire for compatibility, then discarded
  without being trusted).
- **A caller-supplied `TRANSFORMS` or `PATCH` property is rejected on the elevated install path.**
  Either can name a transform or a patch package, and either can carry a custom action that runs
  with the same elevated rights as the install itself. `ValidateAdditionalArgs` now rejects both
  property names outright. This does not affect the companion's own secret-property transform: that
  transform is generated by the companion itself, downstream of this check, from properties it
  places directly into a staging directory it owns, never from a caller-supplied `TRANSFORMS`/`PATCH`
  value.

## Consequences

**Breaking change: an elevated per-machine MSI install now requires a publisher signature the
companion's own baked key set trusts.** Before this change, the companion installed whatever file
the engine told it to, once the bytes matched the hash the engine sent. After this change, an
unsigned bundle, a bundle signed by a key that is not in the companion's baked set, and a
hand-authored `--manifest` per-machine install all fail the elevated install outright. Baking a
publisher key into the elevation companion is now a prerequisite for shipping a per-machine
installer, not an optional hardening step. A publisher who has not baked a key needs to do so
before their next per-machine release; see `documentation.html` §23 for how baking a key already
works for the engine, and note that the companion needs the same `-p:FalkForgeTrustedKey` passed
at its own publish step, since it is a separate binary with its own baked set.

**A caller-supplied `TRANSFORMS`/`PATCH` property is refused, with no signed alternative yet.**
Before this change, an author could pass a transform or patch through to an elevated per-machine
install via `additionalArgs`. That path is closed outright by this change, not replaced by a
signed equivalent. Re-enabling author-declared transforms and patches on the elevated path, bound
to the same signed-manifest mechanism this ADR adds, is planned follow-up work, not part of this
change.

**Version and rollback binding stay out of scope.** This change proves the MSI came from a
publisher key the companion trusts, at the bytes the publisher actually signed. It does not bind
which version of that publisher's software may be installed, so a caller who already has access to
run the elevated companion at all may install any MSI that publisher genuinely signed, not only
the specific one the engine's own upgrade or rollback logic intended for this call. That question
is unrelated to the trust anchor this ADR builds and is not addressed here.

**The moved types keep a namespace that no longer matches their assembly.** `TrustPolicy` and
`PayloadIntegrityGate` live in `FalkForge.Engine.Protocol` now but still declare `namespace
FalkForge.Engine.Integrity`, kept that way so no caller in either the engine or the companion had
to change an import as part of this move. Renaming the namespace to match its new home is a purely
cosmetic follow-up, not attempted here.
