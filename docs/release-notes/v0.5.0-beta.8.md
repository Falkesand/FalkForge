# FalkForge v0.5.0-beta.8

This release closes a gap the elevated companion process has carried since it first started
re-verifying file bytes: it trusted a hash the caller sent it, not a signature it checked itself.
It now checks a publisher signature against a trust anchor baked into its own binary, and it stops
trusting a caller-supplied `TRANSFORMS`/`PATCH` property on that path. Read Breaking changes below
before publishing an elevated per-machine installer built with this release.

## Security: the elevation companion now verifies publisher authorship against its own baked key set, before installing anything

`FalkForge.Engine.Elevation` is the process that runs as SYSTEM to carry out a per-machine MSI
install. It could previously verify that the file it was about to install matched a hash, but that
hash came from the same unelevated engine process the elevated install exists to protect against.
A caller with control over that unelevated process could send whatever hash matched a file it had
already placed, and the elevated side would verify it and install it.

The companion now bakes its own trusted publisher-key set at build time, the same mechanism the
unelevated engine already used to decide which bundle signatures to trust, and independently
verifies the installer manifest's signed integrity envelope against that set before installing an
MSI. The hash it binds the file to is the one inside the verified signature, never a value the
caller asserted. `TrustPolicy` and `PayloadIntegrityGate`, previously private to the engine, moved
into the shared `FalkForge.Engine.Protocol` assembly so the companion can call the same
verification code instead of carrying a second copy.

An empty baked key set fails closed: a companion built without a publisher key refuses every
elevated MSI install rather than silently trusting whatever it is handed.

## Security: a caller-supplied TRANSFORMS or PATCH property is rejected on the elevated install path

A transform (`.mst`) or a patch (`.msp`, itself a container of transforms) can carry a custom
action, so accepting one from the caller on an elevated install is arbitrary code execution as
SYSTEM. The companion now rejects any `TRANSFORMS` or `PATCH` property arriving over the wire for
an elevated install. This does not affect the companion's own secret-property transform, which it
generates itself, in a staging directory it owns, downstream of this check.

## Breaking changes

- **An elevated per-machine MSI install now requires a publisher signature the companion's own
  baked key set trusts.** Previously, the elevated companion installed whatever file the
  unelevated engine told it to, once the bytes matched an asserted hash. Now, an unsigned bundle,
  a bundle signed by a key outside the companion's baked set, and a hand-authored `--manifest`
  per-machine install are all refused. If you ship a per-machine installer, you now need to pass
  `-p:FalkForgeTrustedKey=<fingerprint>` when publishing `FalkForge.Engine.Elevation`, the same way
  you already do for `FalkForge.Engine` — the companion is a separate binary with its own baked
  set, so baking the key into the engine alone is not enough. See `documentation.html` §23 ("Who
  the Installer Trusts") for how key baking works today.
- **A caller-supplied `TRANSFORMS`/`PATCH` property on an elevated install is refused outright,
  with no signed alternative in this release.** If you passed a transform or a patch through to a
  per-machine install this way, that path no longer works. Re-enabling author-declared transforms
  and patches through a signed mechanism is planned, not shipped in this release.

## Known limitations / in progress

- Author-declared transforms and patches have no signed path back onto elevated installs yet (see
  above).
- The trust anchor this release adds proves publisher authorship and binds installed bytes to a
  signed hash. It does not bind which version of a publisher's software may be installed at the
  elevation boundary; that is unrelated to this change and remains open work.

See `docs/adr/0012-elevated-companion-baked-publisher-trust.md` for the full design and
consequences.

## Requirements

- Windows, to *build* MSI/MSM/MSP/MST output (P/Invokes `msi.dll`). Bundle compilation and the
  decompiler's bundle path are cross-platform; MSI compilation, inspection, and the WiX-Burn
  decompiler are Windows-only.
- .NET 10 SDK.
