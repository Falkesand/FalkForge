# FalkForge v0.5.0-beta.8

This release closes a gap the elevated companion process has carried since it first started
re-verifying file bytes: it trusted a hash the caller sent it, not a signature it checked itself.
It now checks a publisher signature against a trust anchor baked into its own binary, and it stops
trusting a raw `TRANSFORMS`/`PATCH` property sent over the wire for an elevated install. An author
who needs a transform on an elevated install still has a way to get one: `.Transform(id, mstPath)`
declares it at build time, so it ships as a signed payload the elevated side can verify before
applying it. Read Breaking changes below before publishing an elevated per-machine installer built
with this release.

## Security: the elevation companion now verifies publisher authorship against its own baked key set, before installing anything

`FalkForge.Engine.Elevation` is the process that runs as SYSTEM to carry out a per-machine MSI
install. It could previously verify that the file it was about to install matched a hash, but that
hash came from the same unelevated engine process the elevated install exists to protect against.
A caller with control over that unelevated process could send whatever hash matched a file it had
already placed, and the elevated side would verify it and install it.

The companion now bakes its own trusted publisher-key set at build time, the same mechanism the
unelevated engine already used to decide which bundle signatures to trust, and independently
verifies the installer manifest's signed integrity envelope against that set before installing an
MSI. The hash it binds the file to is the one inside the verified signature, never a value the
caller asserted. `TrustPolicy` and `PayloadIntegrityGate`, previously private to the engine, moved
into the shared `FalkForge.Engine.Protocol` assembly so the companion can call the same
verification code instead of carrying a second copy.

An empty baked key set fails closed: a companion built without a publisher key refuses every
elevated MSI install rather than silently trusting whatever it is handed.

## Security: a caller-supplied TRANSFORMS or PATCH property is rejected on the elevated install path

A transform (`.mst`) or a patch (`.msp`, itself a container of transforms) can carry a custom
action, so accepting one from the caller on an elevated install is arbitrary code execution as
SYSTEM. The companion rejects any `TRANSFORMS` or `PATCH` property arriving over the wire as a
caller-supplied argument for an elevated install. This does not affect the companion's own
secret-property transform, which it generates itself, in a staging directory it owns, downstream of
this check. It also does not affect a transform the bundle author declared and signed at build time
(next section) — that transform never arrives as a `TRANSFORMS`/`PATCH` argument in the first
place.

## Feature: an author can declare a signed MSI transform for an elevated install

A bundle package can declare an MSI transform with `.Transform(id, mstPath)` on the bundle package
builder. The transform's bytes are hashed and embedded as a signed bundle payload keyed by `id`,
and a signed map in the integrity envelope records which package each transform id belongs to.

At install, the elevated companion applies a declared transform only when both hold: its bytes
match the signed payload entry for that id, and the signed map lists that id under the package
being installed. Either check failing refuses the install. A transform is a signed payload, never
an installable package in its own right — it cannot be renamed onto a different package, added
after signing, or supplied by the caller in place of a declared one; the raw-argument reject in the
previous section stays in force regardless.

Patch (`.msp`) has no equivalent declaration API in this release. A caller-supplied `PATCH`
property stays refused with no signed alternative yet.

## Breaking changes

- **An elevated per-machine MSI install now requires a publisher signature the companion's own
  baked key set trusts.** Previously, the elevated companion installed whatever file the
  unelevated engine told it to, once the bytes matched an asserted hash. Now, an unsigned bundle,
  a bundle signed by a key outside the companion's baked set, and a hand-authored `--manifest`
  per-machine install are all refused. If you ship a per-machine installer, you now need to pass
  `-p:FalkForgeTrustedKey=<fingerprint>` when publishing `FalkForge.Engine.Elevation`, the same way
  you already do for `FalkForge.Engine` — the companion is a separate binary with its own baked
  set, so baking the key into the engine alone is not enough. See `documentation.html` §23 ("Who
  the Installer Trusts") for how key baking works today.
- **A caller-supplied `TRANSFORMS`/`PATCH` property on an elevated install is refused outright.**
  If you passed a transform or a patch through to a per-machine install this way, that path no
  longer works. Declare the transform instead with `.Transform(id, mstPath)` on the bundle package
  so it ships as a signed payload the elevated side can verify (see above). Patch has no
  declaration API in this release, so a caller-supplied `PATCH` property stays refused with no
  signed alternative.
- **The Protocol signing helpers gained an optional trailing parameter.**
  `EcdsaManifestSigner.Sign`/`SignAsync` and `IntegrityEnvelopeCodec.ComputeSignedBytes`/`Sign`
  each gained an optional trailing parameter carrying the new transform-association data. Existing
  call sites compile unchanged, so this is source-compatible. It is a binary break: an external
  assembly built against the old signature will not load against this release without recompiling.
- **`IInstallerEngine` gained `SetLicenseAccepted(bool accepted)`, with no default implementation.**
  A custom engine that implements this interface directly, rather than using the built-in
  `EngineClient` or `NullInstallerEngine`, stops compiling on upgrade until it adds the method.
  This is deliberate: a no-op default would keep such an engine compiling while silently failing
  the licence gate the method exists for, so a licensed installer would fail at plan time with no
  compiler signal that anything was missing. See `documentation.html` §11.7 ("IInstallerEngine")
  for what to implement and a reference implementation in `EngineClient`.

## Known limitations / in progress

- Patch (`.msp`) has no declaration API yet, so a caller-supplied `PATCH` property has no signed
  path onto an elevated install (see above).
- The trust anchor this release adds proves publisher authorship and binds installed bytes to a
  signed hash. It does not bind which version of a publisher's software may be installed at the
  elevation boundary; that is unrelated to this change and remains open work.

See `docs/adr/0012-elevated-companion-baked-publisher-trust.md` and
`docs/adr/0013-signed-package-bound-transforms.md` for the full design and consequences of both
changes.

## Requirements

- Windows, to *build* MSI/MSM/MSP/MST output (P/Invokes `msi.dll`). Bundle compilation and the
  decompiler's bundle path are cross-platform; MSI compilation, inspection, and the WiX-Burn
  decompiler are Windows-only.
- .NET 10 SDK.
