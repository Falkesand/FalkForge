# FalkForge v0.5.0-beta.9

**Release rule: the compiler, `FalkForge.Engine.Runtime.win-x64`, and the `forge` CLI move together.**
From this release the signed integrity envelope is version 3, and the version number is part of the
signed message. An engine or elevation companion built by an earlier release refuses every bundle this
compiler signs with a signature error, and this compiler refuses to embed an engine stub or companion it
can identify as older (BDL038). A `forge verify` from an earlier release reports every MSI this compiler
builds as tampered, because there is no build-time check that can see which CLI will later verify the
MSI. Upgrade the compiler, the runtime package, and the CLI together. See Breaking changes below for what
this means for an already-installed bundle.

This release adds a signed, per-package allowlist of the MSI property names a bundle UI may set during
an elevated install, closing the gap where the elevated companion trusted any property name the caller
sent it.

## Security: the elevated install now sets only the properties the publisher signed

`BundlePackageBuilder.AllowElevatedProperty(params string[] names)` declares, per package, which MSI
property names the elevated companion accepts for that package. The names are signed into the integrity
envelope. The elevated companion checks every name against that list before `msiexec` runs as SYSTEM, on
both channels a value can travel: the command line (`Engine.SetProperty`) and the secure channel
(`Engine.SetSecureProperty`). A name outside the list is refused and the install does not start. A
package that declares nothing accepts no property on the elevated path.

The engine presents every property the UI set to every package's plan action, not only to the package
the UI meant it for. A bundle with more than one per-machine MSI package must declare a given property on
every one of them, or the companion refuses the packages that did not declare it. This check runs only
when the elevated companion installs the package; an engine process that is already running elevated
installs per-machine packages in-process instead, and that path does not enforce the allowlist. Test a
bundle unelevated to exercise the companion and this check.

Names must match `[A-Z_][A-Z0-9_.]*`; `TRANSFORMS` and `PATCH` are rejected at build time (BDL037), since
either would let a caller redirect a SYSTEM install to arbitrary code. `ADDLOCAL` is added to the signed
list automatically for a package with `EnableFeatureSelection`, because the runtime planner stamps that
property for such packages.

## Feature: BDL038 refuses an engine stub or elevation companion older than the compiler

A compiler that signs envelope version 3 needs an engine and a companion of the same or a newer release,
because both verify the envelope they were built to understand. BDL038 checks the `ProductVersion`
resource of the engine stub and the elevation companion about to be embedded against the compiler's own
version, and refuses the build if either is older. A binary that reports exactly `1.0.0` with no
prerelease is refused the same way while the compiler is still below 1.0.0: that is the .NET SDK's
default version, not a real release, and is what a runtime rebuilt from a `FalkForge.Engine.Sources`
package older than this release reports (its templates set no `<Version>` before now), not a newer
runtime that happens to sort above the compiler. Rebuild from the matching Engine.Sources package or
publish a matching runtime. When the compiler cannot read or parse a version, it embeds the binary and
logs a BDL038 warning instead of refusing. That warning reaches a log only when the caller building the
bundle set `BundleCompiler.Logger`. `forge build` sets it, so the warning shows up there; the fluent
`new BundleCompiler().Compile(...)` path, the project template, Studio, and `DeltaBundleCompiler` pass no
logger, so the same warning is silent on those paths.

## Other changes since beta.8

- The elevated companion refuses any envelope below version 3, so a v1 or v2 manifest cannot be replayed
  through a beta.9 companion. Uninstall and trust-state advance keep accepting version 2, since neither
  has a property channel.
- Engine sources templates and the packaged engine stamp the release version into the rebuilt engine and
  companion.

## Breaking changes

- **The signed integrity envelope moves to version 3, and the version is part of the signed message.**
  Every install verifies through a matched compiler/runtime/CLI set (see the release rule above). Publish
  the compiler, `FalkForge.Engine.Runtime.win-x64`, and the `forge` CLI together, all at 0.5.0-beta.9 or
  later.
- **`IntegrityEnvelopeCodec.ComputeSignedBytes`, `EcdsaManifestSigner.Sign`, and
  `EcdsaManifestSigner.SignAsync` gained trailing parameters.** A caller compiled against 0.5.0-beta.8
  binds to the old parameter list at its own compile time; that call site fails at runtime with
  `MissingMethodException` against this release's assembly until it is recompiled.
- **Updating an installed bundle from 0.5.0-beta.8 or earlier does not work through the update channel.**
  Every installed release up to and including 0.5.0-beta.8 verifies a downloaded update with its own
  engine before launching it, and that engine reads the version-3 envelope as tampered. With the default
  `ShowDownloadErrors = false`, the installed bundle discards the download and reports no update; with it
  on, the user sees an INT001 dialog saying the bundle may have been tampered with. Neither is a sign of
  an attack. Publish the first 0.5.0-beta.9 bundle as a download the user runs by hand; it carries its own
  engine and installs over the old one. Updates between bundles built with 0.5.0-beta.9 or later work
  through the update channel as before. Text you can give end users:

  > The automatic update to this version does not run. Download and run the new installer once. Later
  > updates work automatically again.

## Known limitations / in progress

- A publisher who wants to allowlist elevated properties for an existing package has to add
  `.AllowElevatedProperty(...)` and rebuild; there is no way to widen the list without re-signing.
- Value constraints are out of scope for this release. Only property names are allowlisted, not the
  values a caller may set for an allowlisted name.

## Requirements

- Windows, to *build* MSI/MSM/MSP/MST output (P/Invokes `msi.dll`). Bundle compilation and the
  decompiler's bundle path are cross-platform; MSI compilation, inspection, and the WiX-Burn
  decompiler are Windows-only.
- .NET 10 SDK.
