# FalkForge v0.5.0-beta.5

This is the fifth public beta. Where beta.4 was a security-and-honesty beta, beta.5 closes a
long-standing capability gap instead: .NET runtime detection — previously a bundle-engine-only
feature that made a JSON `dotnet` block a hard build error — now emits real MSI-native detection
tables, so standalone-MSI authors get the same runtime gating the bundle engine already had.
Alongside that, engine log entries now redact secret-keyed properties before they are written, and
a resource leak on a UI-launch failure path is fixed. The rest of the cycle was housekeeping —
decomposing another oversized file, deduplicating Cabinet callback code, and closing delta test
debt — in the same spirit as prior betas.

## Shipped this beta

- **.NET runtime detection now emits real MSI-native tables — closes the standalone-MSI gap
  documented since beta.3.** Previously, a `.NET` block in JSON config was a hard build error
  (JSN019), documented as "bundle-engine, detect-time-only feature with no standalone-MSI
  representation" — the C# fluent API's `DotNetExtension` only fed the bundle engine's own detect
  phase and authored no MSI tables. `DotNetExtension.AddSearch()` now emits real `Signature` /
  `DrLocator` / `AppSearch` rows (plus an optional `LaunchCondition` when a `Message` is set) via
  `DotNetSearchPlanner`, and the JSON config path (`JsonConfigLoader`) wires straight into the same
  extension so JSON and C# authoring produce identical tables. The JSN019 error is gone for `.NET`
  blocks specifically; other JSN019 causes are unaffected. Landed with new validation rules:
  `NET001` (`VariableName` required), `NET002` (`MinimumVersion` required), `NET003` (duplicate
  `VariableName`), `NET004` (rejects `Sdk` — the SDK has no shared-framework directory to search —
  and rejects unrecognized runtime-type values), `NET005` (`VariableName` must be a legal PUBLIC
  MSI property identifier, all-uppercase `[A-Z_][A-Z0-9_.]*` — a private/lowercase property isn't
  reliably populated by the standard `AppSearch` action, and an illegal name can be evaluated by
  `msiexec` as an always-true `LaunchCondition` expression), `NET006` (`AddSearch(null)` returns a
  typed failure instead of throwing), and `NET007` (unrecognized `Platform` value rejected). Demo
  32 (`32-ext-dotnet`) now exercises the real detection end to end, with a gated live e2e alongside
  the existing unit coverage.
- **Engine log redaction: secret-keyed properties are now masked before a log entry is written.**
  `LogRedactor` checks each structured log property's *key* (not its value) against a deny-list —
  `password`, `passwd`, `pwd`, `secret`, `token`, `credential`, `apikey`, `privatekey`,
  `passphrase`, `authorization`, `bearer`, `connectionstring`, `signingkey`, `pfx`, `pem` —
  normalizing separators first so `api-key`, `API_KEY`, and `ApiKey` all match the same `apikey`
  token. **This is props-only and does not fully close the gap:** the free-text `message` field and
  `exception.message` (the raw `Exception.Message` text, e.g. a `SqlException`'s connection string)
  are NOT scanned — there is no reliable, low-cost way to detect an embedded secret in opaque
  pre-formatted text without a false-positive-prone heuristic scanner. Callers must pass secrets as
  structured properties, not interpolate them into log messages or let them reach exception text,
  for this redaction to see them.
- **Fixed a resource leak: a failed UI-process launch during bootstrap no longer leaks the init
  pipe.** If `Process.Start` for the UI process failed, the engine returned an error without
  disposing the `NamedPipeServerStream` it had already created for secret delivery. It now disposes
  the pipe before returning.

Under the hood: `FalkForge.Engine/Program.cs` — flagged as an oversized file in the last assessment
— was decomposed from roughly 800 lines down to under 200 by extracting `BootstrapperRunner`,
`EngineInvocationArgs` parsing, `EnginePayloadTrust`, `SelfExtractionMode`, and several smaller
helpers into their own files, all behavior-preserving. The duplicated Cabinet FCI/FDI
alloc/free/`MapOpenFlags` callback code was consolidated into one shared shim. Delta bundle
reconstruction picked up additional fail-loud test coverage (unreadable basis, zip-slip, temp
cleanup) closing out the remaining delta test debt (C15) noted after the delta-runtime-gap fix.
Stryker.NET mutation testing was wired up for five trust-critical projects as a periodic,
non-gating tool — see the reliability caveat below before reading anything into the scores it
produced.

## Known limitations / in progress

- **The live paths (real bundle install/rollback, IIS apply, feature-picker `ADDLOCAL`, external-
  container network download, turnkey UI, per-culture install UI) are built and unit-proven but
  only exercised end-to-end under `FALKFORGE_REAL_SYSTEM_E2E=1`** on a real, elevated machine — see
  `docs/testing/real-machine-verification.md` for the runbook. None of these run in CI.
- **MSIX build is not available via `forge build` or the MSBuild SDK** — it's script-only today,
  via `InstallerMsix.BuildMsix()` / `InstallerMsix.BuildMsixBundle()` called directly from a build
  script.
- **Mutation-testing scores are directional, not authoritative.** The two `coverage-analysis` modes
  Stryker can run under this repo's MTP-based test runner — `perTest` and `off` — disagree by up to
  ~25 percentage points on identical code, and the upstream MTP runner itself is still preview.
  Treat any mutation score in `docs/testing/mutation-testing.md` as a lead to investigate by hand
  (reproduce the mutation, run the affected tests, confirm a failure), not as a quality gate or a
  number to cite on its own.
- **`DefaultRebuildRunner`'s timeout/cancel branch (`forge verify --rebuild`) is covered by neither
  the unit seam nor the opt-in E2E suite** — the `IRebuildRunner` seam replaces the whole class, and
  the E2E suite's rebuilds succeed rather than time out, so the kill-process-tree /
  `OperationCanceledException` path is unverified by either layer.
- **Engine log redaction covers structured properties only** — free-text log messages and
  exception messages are not scanned; see the redaction note above.

## Requirements

- Windows, to *build* MSI/MSM/MSP/MST output (P/Invokes `msi.dll`). Bundle compilation and the
  decompiler's bundle path are cross-platform; MSI compilation, inspection, and the WiX-Burn
  decompiler are Windows-only.
- .NET 10 SDK.
