# FalkForge v0.5.0-beta.6

This is the sixth public beta. Where beta.5 closed a capability gap, beta.6 is dominated by two
beta-blocking upgrade-path bugs and a wide sweep of fluent-API inputs that compiled, validated, and
did nothing at runtime.

`ProductCode` is now deterministic by default (issue #61) and `MajorUpgrade`'s `FindRelatedProducts`
action is now actually scheduled (issue #65) — together these are why a rebuild of the same version
previously installed side by side instead of replacing the original, and why `MajorUpgrade` did
nothing at all. Both are fixed, and both change observable behavior: the same-version rebuild-and-
reinstall loop that used to install messily under beta.5 now fails outright with error 1638 unless you
bump the version or pass `REINSTALL=ALL REINSTALLMODE=vomus` — see the `ProductCode` section below.
**This is the widest blast radius in the release: `PackageBuilder.Build()` gives every package an
implicit `Upgrade` table when `MajorUpgrade` isn't configured, so the downgrade-blocking launch
condition going live from the `FindRelatedProducts` fix affects every FalkForge package, not only ones
that call `.MajorUpgrade(...)`** — see the `MajorUpgrade` section below for the two independent
opt-out switches.

Runtime dependency enforcement (`DependencyProvider`/`DependencyConsumer`) is now genuinely wired into
install/uninstall instead of being decoration, alongside a related registry-key-validation gap closed
on the unprivileged write path. ODBC driver/data-source authoring, `PropertyModel` security flags
(`IsHidden`/`IsSecure`/`IsAdmin`), Restart Manager's actual shutdown behavior (plus a new full-UI
dialog and a closed keyboard tab cycle), and several smaller previously-inert options (merge-module
dependencies, transform `SetProperty`, constructor-injected filesystem, MSIX file-type-association and
protocol registration) all move from silently-accepted-and-ignored to actually working this release.
Install conditions on built-in variables (`VersionNT`, `Privileged`, `RebootPending`) now see real
machine state in both directions — some packages that were always silently skipped now install, and
some that always installed are now correctly skipped.

Separately, SBOM/integrity attestation was hashing source files after packaging instead of the bytes
that actually shipped — a real TOCTOU, found in the MSI compiler and independently in the MSIX
compiler. A long list of breaking changes accompanies this cycle, mostly unwired features being
deleted outright (parallel cabinets, the file-sequencing strategy machinery, `MsiRecipeBuildOptions`,
dead `PipelineContext` members, several unhonoured MSIX inputs) plus the SBOM default format changing
from the never-honoured `Spdx` to the `CycloneDx` bytes every build has always actually shipped.

**Release channel note:** all `v0.5.0-beta.1` through `v0.5.0-beta.5` tags have since been retroactively
marked as GitHub pre-releases, and `v0.5.0-beta.6` continues that via the release workflow's
`--prerelease` flag. With every existing release marked pre-release, `GET /releases/latest` returns
404 — no release carries the "Latest release" badge, which is correct for a product with no stable
release yet.

## New: runtime dependency enforcement (was decoration; now live) — behaviour change for uninstalls

`BundleBuilder.DependencyProvider(...)` / `.DependencyConsumer(...)` have existed since early betas and
were faithfully recorded in the manifest, but nothing ever read them at runtime: `DependencyDetector`
(`DetectBlockingDependencies` / `DetectUnsatisfiedProviders`) was fully implemented and unit-tested, yet
had zero callers anywhere in the pipeline, and there was no write side at all for the bundle-runtime path
(only the MSI-table contributor wrote the WiX-compatible registry layout, for Windows Installer's own
writer, at MSI install time — a different mechanism). Declaring a provider or a consumer had no observable
effect on any install or uninstall.

This is now wired end to end:

- **Uninstall is refused** (exit code 1, `ErrorKind.PlanningError`) while another installed product's
  consumer registration still references a provider key this bundle declares. The refusal message names
  both the provider key and the dependent key(s).
- **Install is refused** when a required `DependencyRequirement` provider is missing or version-unsatisfied
  — with one caveat: a provider's uninstall removes only its own registration's *consumer* entries, never
  its provider row, so a stale provider row left behind by an incomplete cleanup can make an actually-gone
  dependency read as satisfied. This is not an unconditional guarantee; see the "stale provider" note in
  &sect;9.3e for the exact failure mode and why it isn't auto-collected.
- **`--ignore-dependencies`** bypasses both checks. It is NOT implied by silent/unattended mode — an
  automated uninstall that would break a dependent still gets refused unless this flag is explicitly
  passed.
- Both checks read **both** `HKLM` and `HKCU` under `SOFTWARE\Classes\Installer\Dependencies\` — a
  per-user consumer of a per-machine provider (or the reverse) is a real shape. `PerUser`-scoped bundles
  write directly to `HKCU`; `PerMachine`-scoped bundles write to `HKLM` through the elevated companion
  (a new `DependencyRegistration` elevated command, separate from the general-purpose `RegistryWrite`
  command, whose allowlist permanently reserves `SOFTWARE\Classes\` and stays that way).
- The uninstall check fails **closed** on a registry read error (access denied) — an unknown state is
  never treated as "nothing depends on this." A registration-write failure after an otherwise-successful
  apply never fails the install/uninstall itself, but the two directions log at different severity: an
  UNINSTALL-side write failure is logged at `LogLevel.Error` (this bundle's own consumer entry was NOT
  removed and may permanently block a future uninstall of the provider it depends on), while an
  INSTALL-side write failure is logged at `LogLevel.Warning` (the install result itself is unaffected).
- **The unprivileged and elevated write paths now share one key-segment validation guard.** This entire
  runtime-dependency-enforcement feature — including `DependencyRegistrar`, the unprivileged `PerUser`
  write path in `ApplyStep`, and the elevated `DependencyRegistrationCommand` — is new in this beta.6
  cycle; none of it existed at `v0.5.0-beta.5`. Partway through development, `DependencyRegistrar` (the
  writer shared by both paths) initially validated provider/consumer keys only on the elevated command's
  side, not the unprivileged `PerUser` side: an attacker-authored manifest with an empty, `\`, or `/`
  `ConsumerKey` could have reached `IRegistry.SetStringValue`/`DeleteKey` unfiltered on that path — a
  registry-path-traversal shape outside `SOFTWARE\Classes\Installer\Dependencies\`. **This gap was
  introduced and closed entirely within this branch and was never present in any tagged release** —
  `RegisterProvider`/`RegisterConsumer`/`UnregisterConsumer` now validate every key segment through the
  same `DependencyRegistrationPaths.IsSafeKeySegment` guard on both paths before touching the registry.
  No prior release, including beta.5, is affected or requires any action.
- **An unparseable `MinVersion`/`MaxVersion` bound now fails the requirement instead of silently
  skipping it.** `DetectUnsatisfiedProviders` guarded its bound comparison with
  `if (Version.TryParse(...))`, so a typo'd bound silently skipped the whole check and the requirement
  passed regardless of what was actually installed.

See &sect;9.3e in `documentation.html` for the full behaviour, registry layout, and how to clear a stale
registration.

**Audit before upgrading past this beta if you author `DependencyProvider`/`DependencyConsumer` bundles:**
an uninstall that previously always succeeded (because the check was never wired) can now be genuinely
refused. Separately — **MSI-authored dependencies from `FalkForge.Extensions.Dependency` predate this
change and are unaffected by it going forward, but this feature does not retroactively clean up or migrate
any registrations an MSI already wrote to the machine.** A stale MSI-authored consumer entry (from a
product no longer installed) can block a bundle uninstall exactly as a stale bundle-authored one can —
see the "Stale registrations" note in &sect;9.3e for how to identify and clear one, or pass
`--ignore-dependencies` for that one run.

## Fixed: `ProductCode` is now deterministic by default — a rebuild no longer installs side by side (issue #61)

`PackageBuilder.Build()` only derived a deterministic `ProductCode` when `Reproducible()` options were
set (`GuidUtility.CreateDeterministicGuid` over `Name::Manufacturer::Version`); every other build — the
default, and therefore the overwhelming majority of real installers — got a fresh `Guid.NewGuid()` on
every single `Build()` call. Two builds of the exact same product version were therefore two distinct
products as far as Windows Installer was concerned: rebuilding and reshipping the same version installed
*alongside* the original instead of replacing it, leaving two Add/Remove Programs entries. This is the
single most consequential change in this release for anyone upgrading past beta.5 — it changes the
`ProductCode` FalkForge assigns to essentially every MSI it builds.

**`ProductCode` now defaults to a deterministic GUID derived from `Name`, `Manufacturer`,
`<major.minor.build>`, `Architecture`, and `Scope`** — unconditionally, in both normal and
reproducible-build mode, using the same recipe the reproducible path already used:

- **Only `major.minor.build` feeds the key — never the full four-component `Version`.** Windows
  Installer's own `ProductVersion` property only ever records three fields, so a 4th (Revision)
  component — e.g. a CI build number baked into `1.0.0.100` — deliberately does **not** change the
  `ProductCode`. Keying on the full `Version` would let a Revision-only rebuild mint a new
  `ProductCode` while `ProductVersion` (and `RemoveExistingProducts`' `VersionMax` match) stayed
  identical, landing right back in the side-by-side bug this release fixes, through a different field.
  A 2-component `Version` (no `Build` set at all, where `Version.Build` is `-1`) is clamped to `0`
  rather than propagating a negative number into the key.
- **`Architecture` and `Scope` are both part of the key because both change compiled product
  identity**: `Architecture` drives the `SummaryInformation` `Template` field and the Component
  64-bit attribute bit, `Scope` drives `ALLUSERS`. Without them in the key, an ordinary dual-architecture
  ship — the same `Name`/`Manufacturer`/`Version`, built once for x86 and once for x64 — would derive
  the *same* `ProductCode` with a different `Template`, and a `PerMachine` vs. `PerUser` build of the
  same product would fail to install side by side with error 1638 (`ERROR_PRODUCT_VERSION`) instead of
  installing cleanly, with no build-time warning either way.
- **An explicitly assigned `package.ProductCode = ...` still wins** — this default only applies when
  the property is left `null`, exactly as before.
- **`PackageCode` is unchanged** and still varies on every normal-mode build (a fresh `Guid.NewGuid()`
  per `Build()` call); only in reproducible mode does it stay `null` so the compiler derives it from a
  content digest instead. `PackageCode` identifies *these exact bytes*, not the product, and has always
  had different rules than `ProductCode` — this release does not touch that.

**A deterministic `ProductCode` has a real consequence for the most common development loop: a
same-version rebuild no longer installs over itself, it fails.** Same `ProductCode` + same
`ProductVersion` + different bytes is an MSI *small update*, not an automatic replacement — Windows
Installer does not route it through the upgrade mechanism (the emitted `Upgrade` table row's
`VersionMax` match is exclusive, so it matches nothing at an identical version). Running the new MSI
again returns error **1638** (`ERROR_PRODUCT_VERSION`) or opens the maintenance/repair UI instead of
installing. Applying it requires `msiexec /i new.msi REINSTALL=ALL REINSTALLMODE=vomus`. If you author
through `MajorUpgrade`, `MajorUpgradeBuilder.AllowSameVersionUpgrades()` is the fluent-API escape hatch
for this specific case — it flips the emitted `Upgrade` row's `VersionMax` bound to inclusive so a
same-version rebuild upgrades in place instead of requiring the `REINSTALL`/`REINSTALLMODE` workaround.
It only applies to the `MajorUpgrade` path; the implicit non-major `Upgrade` table this release also
starts enforcing has no equivalent same-version opt-in. **Under
beta.5, rebuilding and reshipping the same version installed *side by side* — an ugly outcome, but it
installed. Under beta.6, that same rebuild-and-reinstall loop fails outright with 1638 unless you
either bump the version or pass `REINSTALL=ALL REINSTALLMODE=vomus`.** See &sect;"ProductCode,
UpgradeCode &amp; PackageCode" in `documentation.html` for the full detail.

**Audit before upgrading past this beta:**

- **Every MSI built in non-reproducible mode gets a different `ProductCode` under this release than any
  build made under beta.5 or earlier ever had** — beta.5's non-reproducible `ProductCode` was always a
  fresh random GUID, so no single prior value was ever "the" `ProductCode` for a version to begin with.
  What changes in practice: a beta.5 rebuild of an already-shipped version always drifted to a new,
  unrelated `ProductCode` (the side-by-side bug); a beta.6 rebuild of that same version now reproduces
  the *same* `ProductCode` every time, which is the fix. If you rely on `MajorUpgrade`/`Upgrade` to
  replace an existing install (see the `FindRelatedProducts` fix above), this is what makes that
  replacement actually target the right prior product going forward — but it also means the very first
  beta.6 build of an already-shipped product will **not** match any `ProductCode` a user's machine
  already has installed from beta.5, so that first upgrade still relies on `UpgradeCode` detection, not
  on `ProductCode` matching.
- **Reproducible-mode `ProductCode`s change too, for every version shape** — not only 2- and
  4-component ones. Before this release the reproducible key was `Name::Manufacturer::Version` with no
  `Architecture` or `Scope` in it at all; the new key always appends both. Even a 3-component
  `Version` built at the default `Architecture`/`Scope` therefore hashes a different string than it did
  under beta.5, and gets a different `ProductCode`. Non-default `Architecture` or `Scope` builds are
  additionally affected in a second way: under beta.5 they silently collided with the default-arch/
  default-scope build of the same version (same `ProductCode`, wrong `Template`/`ALLUSERS`); under
  beta.6 each combination now correctly gets its own `ProductCode`.
- If you pin `package.ProductCode` explicitly today, none of the above applies to you — this change
  only affects the default.

See `documentation.html`'s "Concepts" &rarr; "ProductCode, UpgradeCode &amp; PackageCode" section for
the full derivation and guidance on when (rarely) to override it.

## Fixed: install conditions on built-in variables now see real machine state — in BOTH directions

`BuiltInVariables.Populate` (VersionNT, Privileged, ComputerName, RebootPending, and 30+ others)
was wired into `DetectStep` in an earlier beta.6 commit, but the wiring itself had gaps that meant
conditions still did not see real values reliably. This changes which packages install on a real
machine, in both directions:

- **Packages gated on a built-in that were always silently skipped now install.** The WiX-idiomatic
  form authors actually write, `VersionNT >= 603` (undotted integer, per MSI's own major*100+minor
  encoding — 603 = Windows 8.1), always evaluated false regardless of the real OS version: `VersionNT`
  is stored as a `System.Version`, so the integer literal fell through to ordinal STRING comparison
  (`"10.0.26200.0"` vs `"603"`) instead of a numeric one. Any package gated on `Condition.IsWindows10OrLater`
  or a hand-authored `VersionNT >=` / `VersionNTMajor >=` condition in that form now evaluates
  correctly. `Condition.IsPrivileged` ("Privileged") also previously under-reported: it read only
  whether the engine PROCESS itself was elevated, but `FalkForge.Engine` is `asInvoker` and performs
  per-machine work through a separate elevated companion process — on the normal double-click flow
  the process is never elevated even when the install can do per-machine work via the companion, so
  a package gated on `IsPrivileged` was silently skipped on every normal install. `Privileged` now
  reflects whether the INSTALL can perform privileged work (process already elevated, OR an
  elevation companion is configured and available), not just the process token.

- **The dangerous direction — a condition that used to always pass now correctly fails.**
  `NOT RebootPending`-style conditions (skip a package while a reboot is pending) previously always
  evaluated true regardless of the real pending-reboot state, so those packages always installed —
  now they are correctly SKIPPED when a reboot really is pending, which is the intended safety
  behavior but is new observable behavior for any bundle relying on that condition. Similarly, a
  legacy-shim package gated on something like `VersionNT < 10.0` (install only on pre-Windows-10
  hosts) previously always installed on every machine, including modern Windows 10/11, because the
  same empty-string ordinal fallback happened to compare true; it now correctly evaluates false and
  is SKIPPED on modern Windows.

- **`RebootPending` itself gained a new signal and a new fail-closed rule — and a second, previously
  dead signal came back to life at the same time.** Separately from the ordinal-comparison fix above,
  the probe now also checks the Windows Update `RebootRequired` key, which was not probed at all
  before. But `PendingFileRenameOperations` was not a working probe either: it is a registry *value*
  under `Session Manager`, not a subkey of its own, and the old code passed that value's path straight
  to a bare `KeyExists` (subkey-existence) check, which can never see a value — that probe always
  returned false and contributed nothing. Two signals went live in this release, not one. The probe
  also now treats any of its three registry reads coming back unreadable (e.g. ACL-denied) as pending
  rather than silently absent. A `NOT RebootPending` package can therefore now be SKIPPED on a machine
  with no reboot pending at all, purely because one probe could not be read — that is the intended
  fail-closed behavior, not a bug, but it is new observable behavior for any bundle relying on that
  condition.

  **Audit any bundle whose `InstallCondition` references a built-in variable before upgrading past
  this beta** — the fix is correct, but "always ran" and "never ran" are both real, observable
  changes for existing bundles that depended (even accidentally) on the old always-true/always-false
  behavior.

## Fixed: `PropertyModel` security flags (`IsHidden`/`IsSecure`/`IsAdmin`) now actually take effect

`PackageBuilder.Property(name, value, p => p.IsHidden = true)` (and the `IsSecure`/`IsAdmin`
overloads) stored the flag on `PropertyModel`, but nothing on the compile side ever read it —
present in every `0.5.0-beta.1` through `beta.6` release.

- **`IsHidden` had no effect.** The flag was accepted and stored, but no producer read it, so a
  property an author marked hidden was written to a verbose `msiexec /L*v` install log in
  plaintext, with no warning and no build error.
- **`IsSecure` had no effect.** The flagged property was never listed in the compiled MSI's
  `SecureCustomProperties`, so its value did not survive the UI-to-elevated-execute boundary and
  never reached a deferred custom action that needed it — a silently broken install path, not a
  data leak: the value simply never arrived where the author intended it to go.
- **`IsAdmin` had no effect at all**, and no compiled output was ever affected by it either way.

This is fixed by three changes landing together: `PropertyTableProducer` now emits
`SecureCustomProperties` and `AdminProperties` from every property's flags, and a new
`HiddenPropertiesEmitter` merges author-flagged `IsHidden` names with extension-contributed secrets
into the existing `MsiHiddenProperties` row. Three new build-time errors, `PRP001`, `PRP002`, and `PRP003`, can reject a package that previously
compiled without complaint (all three are listed in `docs/validation-error-codes.md`):

- `PRP001` — a property marked `IsSecure` whose name contains a lowercase letter (Windows
  Installer's `SecureCustomProperties` only ever recognizes public property names, and a public
  property name must contain no lowercase letter — digits, underscores, periods, and uncased
  scripts are all still allowed — so a name with a lowercase letter could never have worked
  anyway). **Migration:** rename the property so it contains no lowercase letter.
- `PRP002` — a property named `SecureCustomProperties`, `AdminProperties`, or
  `MsiHiddenProperties` (these are computed and emitted by the compiler itself from every
  property's flags). **Migration:** delete the hand-authored property; use the corresponding
  `IsSecure`/`IsAdmin`/`IsHidden` flag on the property it is meant to cover instead.
- `PRP003` — a flagged property name containing `;` or whitespace. Windows Installer's
  `SecureCustomProperties`/`MsiHiddenProperties`/`AdminProperties` are `;`-delimited lists, so
  either character in a name would corrupt the list or silently merge with a neighboring entry.
  **Migration:** rename the property so it contains neither character.

Also worth knowing now that `IsAdmin` does something: it does **not** mean "restricted to
admin-only access" (documentation previously said this; it was wrong and has no MSI counterpart).
`AdminProperties` means Windows Installer saves the property's value at administrative
installation time (`msiexec /a`), and subsequent per-machine installs from that admin image use
the saved value.

The parallel path for *extension*-contributed secrets (`ExecutionStep.HiddenProperties`,
aggregated by `ExecutionStepEmitter` into the same `MsiHiddenProperties` row) worked correctly
throughout — an IIS or SQL extension password was genuinely scrubbed from the log the whole time.
That working implementation, sitting right next to the inert author-facing flags, is most of why
the gap went unnoticed for six betas.

If a package built before this release marked a secret property `IsHidden`, that value will appear
in cleartext in the verbose install logs produced by that package; rebuilding with this release is
enough to fix it going forward. Separately, and independent of this fix: Microsoft's own
`msiexec` logging policy has a `Debug` value of `7` that additionally writes command-line input to
the log — when that policy is set, a property's value can still appear in the log even though it
is listed in `MsiHiddenProperties`, because that policy captures the raw command line rather than
going through the normal property-logging path `MsiHiddenProperties` scrubs.

`forge migrate`/`forge verify --rebuild` round-trips a rebuilt `MsiHiddenProperties` as a strict
*subset* of the original when the original list named an entry with no backing `Property` table
row — e.g. an extension's deferred-action `CustomActionData` carrier property such as
`SqlDb_AppDb`, set only at run time via `SetProperty` and never authored as a `Property` row. That
name is correctly not fabricated back into a `PropertyModel`, so the rebuild is faithful-but-
narrower. This is not a regression: the row was absent from the reconstructed model entirely
before this fix too, and the narrower list still contains every name that has a real backing row.

## Fixed: `MajorUpgrade` did nothing at all — `FindRelatedProducts` was never scheduled (issue #65, beta blocker)

`MajorUpgradeBuilder` (and the lower-level `UpgradeBuilder`) wrote correct `Upgrade` table rows and
correctly scheduled `RemoveExistingProducts`, but `FindRelatedProducts` — the standard action that
actually reads the `Upgrade` table and sets its `ActionProperty` values (`OLDERVERSIONFOUND` /
`NEWERVERSIONFOUND`) — was never emitted into either sequence. It appeared nowhere in `src/`; grepping
the whole repo turned up only a tutorial and a demo. Without it those properties were never set,
`RemoveExistingProducts` had nothing to remove, and any launch condition referencing them was inert.

**Net effect: `MajorUpgrade` did nothing at all.** Installing `0.3.0` over `0.2.0` installed side by
side, leaving two Add/Remove Programs entries. Downgrade protection never triggered. The `Upgrade`
table rows themselves were correct — which is exactly why this looked like it worked.

This is a wider blast radius than "packages that configure `MajorUpgrade`": `PackageBuilder.Build()`
defaults `Upgrade` to a plain `UpgradeModel()` whenever `MajorUpgrade` isn't configured, so **every
package built through the fluent builder already carries an implicit `Upgrade` table** — including its
`NOT NEWERVERSIONFOUND` downgrade-blocking `LaunchCondition`, which every beta-1-through-beta-6 build
of every FalkForge package has silently authored. That launch condition was **never actually enforced**
on any FalkForge-built package, `MajorUpgrade` or not: with `NEWERVERSIONFOUND` never set, `NOT
NEWERVERSIONFOUND` was vacuously true, every time. This fix makes it live for the first time.

**Fix:** both `InstallExecuteSequenceTableProducer` and `InstallUISequenceTableProducer` now emit
`FindRelatedProducts` whenever the `Upgrade` table would be emitted (either the non-major `Upgrade`
path or `MajorUpgrade`) — tied to the table's existence, not narrowly to `MajorUpgrade`. It is scheduled
at **sequence 25**, before `LaunchConditions` (100). A downgrade-blocking condition on
`NEWERVERSIONFOUND` evaluates at `LaunchConditions` (100), so `FindRelatedProducts` must already have
run by then or the property would not exist yet and the condition would stay silently inert — a
second, quieter version of this exact bug, one step removed. `FindRelatedProducts` reads only the
`Upgrade` table and has no dependency on any earlier action, so running it this early is safe. In
`InstallUISequence`, this also overrides the "no dialogs, no custom UI action = skip the table
entirely" early return: a package with an implicit `Upgrade` table but no authored UI now gets the
full standard UI-sequence baseline (`AppSearch` through `ExecuteAction`) so the UI phase still hands
off to `InstallExecuteSequence` correctly.

**Second fix, same bug, elevation boundary:** scheduling `FindRelatedProducts` was not sufficient on
its own. It runs client-side and unelevated in `InstallUISequence`; Windows Installer then suppresses
the duplicate `InstallExecuteSequence` copy of the same action once the UI-sequence copy has already
run. Without `OLDERVERSIONFOUND`/`NEWERVERSIONFOUND` listed in `SecureCustomProperties`, those
properties never crossed into the elevated server-side process, so any install run through a UI
(anything other than a silent `/qn` install) still installed side by side instead of upgrading — the
same failure this whole fix exists to close, reopened one layer down. `PropertyTableProducer` now adds
both names to `SecureCustomProperties` whenever the `Upgrade` table is emitted, merged into the same
ordinal-sorted set as any author-declared secure properties (deduplicated, not appended) so
`Reproducible()` builds stay byte-identical and a name an author already declared secure is not
duplicated. Silent installs were never affected, since no UI sequence runs for them.

**Audit before upgrading past this beta if you rely on side-by-side installs of different versions
under the same `UpgradeCode`, or if you were never explicitly allowing downgrades and relying on the
guard being inert:**

- **Upgrades now actually happen.** A package that previously installed side by side with an older
  version (because `MajorUpgrade`/`Upgrade` was configured but inert) will now correctly replace it —
  at the `MajorUpgradeBuilder.Schedule(...)`-selected `RemoveExistingProducts` sequence for
  `MajorUpgrade` packages, or the fixed sequence 1450 for the non-major `Upgrade` path. If you were
  relying on the old side-by-side behavior — intentionally or not — this is a breaking runtime change
  for your next release.
- **The default downgrade-blocking launch condition is now live for every FalkForge package that
  carries an `Upgrade` table** — which, because `PackageBuilder.Build()` defaults `Upgrade` to a plain
  `UpgradeModel()` whenever `MajorUpgrade` isn't configured, is effectively every FalkForge package, not
  just ones that configure `MajorUpgrade`. This guard is driven by **two independent switches**
  depending on which path built your package, and they are not interchangeable:
  - Packages configured with `package.MajorUpgrade(...)`: the guard is controlled by
    `PackageBuilder.Downgrade()` (`DowngradeModel.AllowDowngrades`). Call
    `package.Downgrade(d => d.Allow())` to permit downgrades.
  - Every other package — including the common case of never calling `.Upgrade()` or `.MajorUpgrade()`
    at all — carries the implicit non-major `UpgradeModel`, whose guard is controlled by
    `UpgradeBuilder.AllowDowngrades` instead. **`package.Downgrade(d => d.Allow())` has no effect on
    this path.** Call `package.Upgrade(u => u.AllowDowngrades = true)` explicitly if you need downgrades
    to keep working.

  Either way, if you never called the matching method, installing an older `Version` under the same
  `UpgradeCode` will now fail validation where it previously silently succeeded.

- **A hand-scheduled `FindRelatedProducts` action now collides with the compiler's own baseline
  row.** If you diagnosed issue #65 yourself and worked around it by scheduling the action
  explicitly — e.g. `p.ExecuteSequence(seq => seq.Action("FindRelatedProducts").After("AppSearch"))`
  — that build compiled and ran cleanly before this release. `InstallExecuteSequenceTableProducer`
  and `InstallUISequenceTableProducer` now unconditionally add their own `FindRelatedProducts` row
  whenever the `Upgrade` table is emitted (see above), and the merge step for user-scheduled actions
  does not check the baseline list for a name collision — only sequence *numbers* are deduplicated,
  not the `Action` name, which is the table's primary key. Two rows in the same table sharing a
  primary key value fails the build at `PrimaryKeyValidator` (`ErrorKind.Validation`) before the recipe
  ever reaches `msi.dll` — a build-time validation failure, not a literal `msi.dll` insert-row failure,
  but a hard build failure either way, not a silent no-op. **You are
  the person most likely to hit this**: hand-scheduling this exact action is the standard workaround
  for the exact bug this release fixes. **Migration:** delete the hand-scheduled action; the
  compiler now schedules it for you at sequence 25.

- **A `.After("FindRelatedProducts")` / `.Before("FindRelatedProducts")` anchor on some other action
  now resolves to a very different slot.** Before this release, referencing an action the compiler
  had never scheduled fell back to `SeqInstallFiles` (4000), so `.After("FindRelatedProducts")`
  landed at 4001 — inside the install transaction, after `InstallInitialize` (1500). Now that
  `FindRelatedProducts` is genuinely scheduled at sequence 25, the same anchor resolves to 26 —
  before `InstallInitialize` and before every other baseline action except `FindRelatedProducts`
  itself. This is live in this repository's own `demo/09-advanced-msi/Program.cs`, which schedules
  `SetUpgradeFlag` with `.After("FindRelatedProducts")`; for that immediate property-setter the new,
  earlier slot is what the demo always intended, so the demo's behavior improves. But the move is
  silent — nothing warns that an anchor's resolved position changed — and CI does not exercise this
  path by default, since heavyweight demo builds are gated behind `FALKFORGE_E2E=1`. **Audit** any
  `.After("FindRelatedProducts")` or `.Before("FindRelatedProducts")` anchor in your own packages
  and confirm the new, much earlier slot is still what you intended before upgrading past this beta.

See &sect;8.14 in `documentation.html` for the scheduling detail and &sect;"Migrating an Existing
Installer to FalkForge" for the corrected downgrade-blocking description.

## Fixed: `BannerBitmap` docs understated the banner's current rendered size — 493x58 documented, 493x77 actual (issue #67)

`DialogCustomizationModel.BannerBitmap` and `DialogCustomization.BannerBitmap(key)` documented the
banner image as 493x58 px. That number undersold what the control currently renders at: the `Banner`
region (`Layouts.Standard370x270`) is 370x58 DLU, and the classic MSI DLU-to-pixel conversion is 4/3 on
**both** axes — 370 DLU converts to the familiar 493 px, and 58 DLU converts to 77 px, not 58. The width
axis happened to land on the number everyone already knows (493, the classic WiX/MSI banner width); the
height axis was never converted at all, so the docs quietly described one axis in pixels and the other
in raw DLU.

**As of this release, `BannerBitmap`'s docs state what the control area currently is: 493x77 px, not
493x58.** A banner authored to the old 493x58 guidance renders stretched ~1.33x vertically today (a
58px-tall source image scaled up to fill a 77px-tall control area) — easy to mistake for a rendering
artifact rather than a sizing bug. This release fixes the documentation to describe current behavior
accurately; it does not change the `Banner` region or any rendering.

**Open question, not settled by this release:** the `Banner` region's height — 58 DLU — may itself be
the bug, one layer down. The classic Windows Installer / WiX banner control is 370x**44** DLU, which
renders at 493x**58** px — the classic banner size. 58 appearing as both the DLU height here *and* the
classic *pixel* height is the same "pixel value pasted into a DLU field" shape this release's docs fix
addresses one layer up. Corroborating: the region leaves ~15 DLU of dead space between controls —
`Description` ends at DLU Y=43 at most, and `ContentArea` starts at DLU Y=60. If the region height is
later corrected to 44 DLU, the control's actual rendered size becomes 493x58 px again and this
release's 493x77 figure would need to change right back. **This release does not resolve that question
and does not instruct anyone to re-author banner artwork** — re-authoring now, before it is resolved,
risks doing the work twice. If you author banner art today, treat 493x77 as the size that matches
*current* behavior, not as a final, settled dimension.

The `DialogBitmap` (Welcome/Exit background, 493x312 px / 370x234 DLU) and `HeaderIcon` (16x16 DLU)
docs were already internally consistent (both axes converted, or both left in DLU) and are unaffected
— this was specifically a partial-conversion slip on the `Banner` region's *documentation*, and a
repo-wide check found no other occurrence of the same shape.

## New: bitmap dimensions and text safe zones documented (issue #62)

Building on the fix above, `documentation.html` §14 ("MSI Dialog Templates" → "Dialog Customization
API" → "Bitmap Dimensions and Text Safe Zones") now documents, for the stock dialog set: the true
canvas/region/control sizes in both DLU and pixels, the 4/3 conversion ratio itself, and where the
`Description` text and a synthesized `HeaderIcon` actually draw relative to the banner.
`docs/dialog-template-architecture.md` already documented the region sizes in DLU (`Banner` 370x58,
`DialogBmp` 370x234, `HeaderIcon` 16x16) — what was genuinely undocumented anywhere was the pixel
conversion and the resulting text safe zones. An author composing banner art had no way to convert
those DLU sizes to the pixels their art tool works in, or to know where the dialog's own controls would
draw over it, and the first time the gap became visible was on the installer's own first screen, after
the build already succeeded and the MSI already validated.

The practical takeaway: on the 493x77 px banner, `Description` text on interior dialogs occupies
roughly x 33-406, and a synthesized `HeaderIcon` (when set) occupies roughly x 461-482, leaving a
~55px clear strip at x 406-461. The dialog's own title sits at the **left** edge (`TitleRow`, x 20)
— the opposite of where most authors reach for a logo — so custom branding art belongs on the right
side of the banner, not the left.

## Improved: payload-not-found error now names the cause (issue #63)

`ComponentResolver` resolves payload `SourcePath` values against `Environment.CurrentDirectory` — this
was already correct, working-as-designed behavior, but the error an author saw when it failed named
only the already-resolved absolute path, which reads exactly like a typo in a path that was never
wrong. The most common real cause: `dotnet run --project installer/MyApp.Installer` from a repo root
does **not** change the working directory the way plain `dotnet run` from inside the project does, so
a payload path that is correct relative to the installer project fails to resolve.

The failure message (emitted internally by `PackageCodeDerivation`, surfaced as
`ErrorKind.FileNotFound`) now names the actual cause **for a relative path**: the current working
directory the path was resolved against, and the `dotnet run --project` gotcha specifically. A fully
qualified source path is never resolved against the working directory in the first place, so naming
the cwd there would state a cause that cannot be true — an absolute path instead reports plainly that
the file is missing at that location, with no working-directory or `dotnet run` guidance attached.
`docs/tutorials/getting-started.html`'s own "Try it" step used exactly the relative-path broken
invocation (`dotnet run --project demo/01-hello-world` from the repo root, which cannot find
`demo/01-hello-world/payload/hello.txt`) — it now reads `cd demo/01-hello-world` then `dotnet run`,
with the working-directory requirement stated explicitly. Path resolution itself is unchanged by this
release — this is a message-and-documentation fix, not a switch to assembly-relative payload
resolution.

## Fixed: SBOM/integrity attestation hashed source files after packaging, not the bytes that shipped

`IntegritySigner` (MSI) re-opened each `ResolvedFile.SourcePath` and hashed whatever was on disk at
integrity-signing time (step 8.5) — long after the cabinet had already read and frozen those bytes
(step 5). Anything that changed the source file on disk between packaging and signing — a build script
overwriting its output, a concurrent build, a race with an antivirus scanner — produced a signed
attestation for bytes that were never actually shipped inside the MSI. Observed directly while
diagnosing this: the signed attestation recorded a tampered on-disk digest instead of the digest of
the bytes the cabinet had packaged. This was fail-closed, not a trust bypass — `MsiIntegrityVerifier`
re-reads the same (correct) shipped bytes, so a genuinely tampered file failed verification either way
— but a legitimate, unmodified build could sign the wrong digest for its own shipped content, and the
same source-after-packaging pattern was found independently, by checking siblings after fixing the
first occurrence, in the MSI SBOM generator and the **MSIX** SBOM helper — three instances across two
compiler projects (`FalkForge.Compiler.Msi`, `FalkForge.Compiler.Msix`). The bundle path
(`BundleIntegritySigner`, `BundleSbomHelper`) never had this defect: both already hashed the
`ResolvedPayload.Sha256Hash` carried forward from packaging, never re-reading from disk at signing
time. **The MSIX case is different from the MSI ones: `MsixSbomHelper` did not exist at
`v0.5.0-beta.5` at all** — it was introduced and fixed within this same beta.6 cycle, so unlike the
MSI instances there is no prior tagged release whose MSIX SBOM artifacts need auditing for this
specific defect.

- **Digests are now captured at packaging time and carried forward**, never re-read from disk at
  signing time. A file whose source was deleted, replaced, or modified after packaging is now
  correctly reflected (or the build correctly fails) instead of silently attesting to whatever
  happens to be on disk when signing runs.
- **A missing or incomplete digest now fails the build** (`ErrorKind.IntegrityError`) rather than
  silently narrowing the signed payload set — signing a partial file list without saying so is a real
  weakening of the guarantee the signature makes.
- **Every SBOM digest is now validated before being serialized as a checksum claim**, not just
  `Sha1Hash` — `Sha256Hash` went into the same `checksums` array unexamined before this release, for
  both file and package components, and both of the attestation paths accepted a caller-supplied
  `AdditionalComponents` digest with no shape validation at all despite being the artifact that gets
  cryptographically signed. Two new diagnostic codes (`SBM003`, `SBM004`, documented in
  `docs/provenance.md`) name the failure precisely instead of a bare validation error.
- **A real SPDX 2.3 writer was added, and `SbomFormat` now genuinely selects which document an MSI
  `Integrity()` attestation generates and attests** — previously the CycloneDX writer was hardcoded
  regardless of what `SbomFormat` said, so requesting SPDX produced a document labeled `spdx` whose
  bytes were still CycloneDX. Requesting SPDX can now legitimately fail where CycloneDX could not (SPDX
  2.3 §8.4 requires a per-file SHA-1, which CycloneDX does not); attestation stays never-fatal, but a
  skipped attestation for that reason is now logged instead of silently vanishing — conditional on an
  `IFalkLogger` being supplied; `MsiCompiler`'s parameterless and `IFileSystem`-only constructors both
  default it to `null` (no-op), so a caller using either of those still sees a silently skipped
  attestation unless it uses the constructor overload that accepts a logger. **`SbomFormat`'s
  scope is MSI attestations only** — a bundle attestation always emits CycloneDX regardless of
  `SbomFormat`, because a bundle payload entry carries only a SHA-256 and SPDX 2.3 §8.4 requires a
  per-file SHA-1; `BundleIntegritySigner.AttestationFormat` is hardcoded and does not read the setting
  at all. The plain `.Sbom()` sidecar (MSI, bundle, and MSIX alike) is CycloneDX by definition and
  consults no format setting either.

**Audit before upgrading past this beta if you consume the SBOM or integrity attestation from a
FalkForge-built MSI**: the digests you get from this release are computed from the actual shipped
bytes for the first time. If your own tooling previously cross-checked a FalkForge attestation against
a source tree rather than the compiled artifact, that comparison could have been quietly passing on a
coincidence before; it is now checking what it always claimed to check. This audit does not apply to
MSIX (its SBOM helper is new this cycle, so no prior release attested wrong digests) or to bundles
(`BundleIntegritySigner`/`BundleSbomHelper` always hashed the packaging-time digest and never had this
defect).

## Fixed: Restart Manager now actually closes locked-file applications, and a keyboard-only user can decline it

`EnableRestartManagerSupport()` has documented since early betas that Windows will gracefully close
applications holding files the install needs to replace. `PropertyTableProducer` was emitting
`MSIRMSHUTDOWN=2` (do not shut down affected applications), so Restart Manager only ever *detected*
locked files and never closed anything — silent or basic-UI installs proceeded to fail on the locked
file, or succeeded only because nothing happened to be holding it, regardless of what the docs
promised. `MSIRMSHUTDOWN` now correctly emits `0`: Restart Manager shuts down affected applications
during install, and restarts only the ones that registered via `RegisterApplicationRestart`.

The full-UI path had never been implemented at all: no dialog in any of the five stock templates ever
showed the list of applications Restart Manager found, so a full-UI install with `EnableRestartManager`
set could only silently proceed or silently fail — there was no way for Windows Installer to ask the
user anything. This release adds the standard `MsiRMFilesInUse` dialog (authored by `DialogSetProducer`
whenever `EnableRestartManager` is set and a stock dialog set is active; it is not part of any of the
five templates because the installer engine invokes it directly, not via `SpawnDialog` from a sibling
dialog), using the `RadioButtonGroup` control type to offer the shutdown-or-cancel choice.
`RadioButtonGroup` itself has been authorable since beta.5 — what's new this release is that the
compiler finally emits the `RadioButton` table row `MsiRMFilesInUse`'s own shutdown-choice group needs:
per ICE34, a `RadioButtonGroup` control requires a matching `RadioButton` table row for its group
property. **This fix covers only the stock `MsiRMFilesInUse` dialog, whose radio values are wired
internally by `MsiRMFilesInUseDlgBuilder`.** `DialogContent.RadioButtons` — the model property the new
row-emission code reads from — is `internal`; there is still no public authoring API for radio button
values on a custom `CustomDialogTranslator`-authored dialog. A package that hand-authors its own
`RadioButtonGroup` control on a custom dialog still ships an MSI that fails ICE34, exactly as before
this release. Closing that gap is open work, not part of this fix.

**A keyboard-only user could not decline application termination.** `DialogComposer` never set
`Control_Next` on any composed dialog — every stock dialog shipped an all-`NULL` tab chain — which on
an ordinary dialog only breaks Tab-key navigation, but on `MsiRMFilesInUse` made the shutdown-choice
`RadioButtonGroup` keyboard-unreachable: a keyboard-only user was stuck on the seeded default
(`UseRM` — allow shutdown) with no way to Tab to the other option and decline. Every composed dialog
(stock templates, `MsiRMFilesInUse`, custom dialogs, extension-contributed steps) now gets a closed
`Control_Next` tab cycle over its focusable controls, linked in on-screen geometric order — **with two
opt-outs**: a dialog where the author already set any `NextControl` link is left untouched (an
authored partial chain is treated as intentional and never overwritten), and a dialog with zero or one
focusable control gets no chain at all (nothing to link, or a self-loop WiX itself guards against).

Separately, `RestartManagerSession`'s marshalled `RM_PROCESS_INFO` struct layout had a wrong
`CCH_RM_SESSION_KEY` constant (256 instead of the correct 32, additionally misused to size
`strAppName` where `CCH_RM_MAX_APP_NAME` — 255 — belongs), producing a struct 4 bytes too large per
element. This was latent rather than observed in practice: nothing in production ever constructed the
type outside its own unit tests, so no real `RmGetList` call had ever marshalled it. It is fixed as
part of this release and pinned by a new layout test so it cannot silently reappear now that the
full-UI path actually exercises Restart Manager.

**Audit before upgrading past this beta if you set `EnableRestartManagerSupport()`:** a silent or
basic-UI install that previously left locked-file applications running (and then failed or produced
partial results) will now close them, and restart the ones that opted into
`RegisterApplicationRestart`. If you relied on Restart Manager detecting-but-not-closing as a way to
learn about conflicts without disrupting the user's session, that behavior is gone.

## New: ODBC driver and data source authoring — was accepted and silently dropped, now compiles and installs

`FalkForge.Extensions.Util`'s ODBC authoring API (`OdbcDriverBuilder`, `OdbcDataSourceBuilder`) has
existed since early betas, but every part of the pipeline it depends on was either missing or wrong,
so it was dead on arrival end to end:

- **The write schema was missing entirely.** `ODBCDriver`/`ODBCDataSource` targeted a non-built-in MSI
  table without declaring `WriteColumns`, so `ExtensionTableEmitter` hard-failed the build with
  `EXT001` for any package that registered an ODBC driver or data source at all.
- **Fixing the schema alone still installed nothing.** `ODBCDriver.Component_`/`File_` and
  `ODBCDataSource.Component_` are external keys into the compiler-generated `Component`/`File` tables;
  the first fix asked authors for identifiers those tables never expose, so it traded a build failure
  for an unresolvable reference. They are now derived internally from the resolved component/file
  the author's payload path names, the same resolution `EXT001` itself exists to enforce elsewhere. An
  unresolvable or ambiguous `FileName`/`SetupFileName` reference now fails the build instead of shipping
  a dangling key, with an `ODB001`-prefixed message pointing at the cause — `ODB001` is a
  `MissingValueHint` string prefix surfaced through the existing `ErrorKind.CompilationError` path, not a
  separate emitted diagnostic code the way `PRP001`-`PRP003` or `MST003` are.
- **Nothing scheduled the standard actions that make the rows do anything.** Even with a correct write
  schema, Windows Installer only acts on `ODBCDriver`/`ODBCDataSource` rows if `InstallODBC` (5400) and
  `RemoveODBC` (2400) are scheduled — nothing scheduled them, so a package with fully correct rows
  still built successfully and installed nothing. Both are now scheduled automatically (zero rows
  emitted, and the sequence entries omitted, for packages that don't use ODBC).
- **Data-source connection attributes were silently dropped.** `OdbcDataSourceBuilder.Property(key,
  value)` stored the attribute on the model, but no contributor ever turned it into an
  `ODBCSourceAttribute` row, so a `Server`/`Database`/etc. attribute an author set never reached the
  compiled MSI. `ODBCSourceAttribute` rows are now emitted for every declared attribute.

**If you already worked around the `EXT001` build failure or the previously-silent no-op** by
authoring ODBC registration some other way (a custom action, a hand-authored custom table), you are
not affected by the schema/scheduling fixes changing your installer's behavior — but you may now be
able to delete that workaround in favor of the fluent API, which works end to end for the first time
in this release.

## Fixed: `forge migrate` could report "all mapped" when it was not

`MigrationMsiEmitter.BuildNotMigratedSection` inspects the reconstructed `PackageModel` to decide
whether to print "All present features were mapped." — a genuine all-clear a migration author relies
on to know the generated project needs no manual review. Two ways that claim could be wrong:

- **A failed table-name query was treated as "the MSI has no tables to worry about."** If the real
  MSI's `_Tables` catalog query failed partway through decompilation, the recipe was built anyway with
  an empty `AllTableNames`, and the unmapped-table check compares against that list — zero known
  tables reads as zero unmapped tables, so the report printed a false all-clear instead of reflecting
  that the migration was actually incomplete. `MsiDecompiler.DecompileToRecipe` — the exact entry
  point `forge migrate` calls — now returns a failure instead of a recipe with a lying empty table
  list.
- **`Media` was missing from the compiler's list of tables it knows how to map**, so the migration
  report claimed `Media` rows were dropped and unrecoverable, even though `MsiPayloadExtractor` reads
  `Media.Cabinet` directly to locate installable payload — the data was never actually lost, only
  mis-reported as lost. `Media` is now correctly listed as a mapped table.

Both are report-accuracy fixes only — no change to what a migration actually reconstructs. If a past
`forge migrate` run told you "all present features were mapped" for an MSI with unusual tables or that
hit a `_Tables` query failure, that claim may not have been trustworthy; re-run the migration under
this release for an accurate report.

## Fixed: `Result<T>.Success` rejected legitimate `null` values

`Result<T>.Success(value)` threw `ArgumentNullException` when `value` was `null` — including for
callers whose `T` is itself nullable (`Result<string?>`, `Result<SomeClass?>`), where a successful
result carrying `null` (e.g. "operation succeeded, no match found") is a legitimate, distinct outcome
from failure. `Result<T>.Success(null)` for a nullable `T` now succeeds instead of throwing.

**This is not purely a redundant-guard removal.** Nullable-reference analysis is a compile-time
diagnostic (`CS8604`), not a runtime barrier — it does not stop a caller who suppresses with `!`, and
`TreatWarningsAsErrors` is FalkForge's own build setting, not something a consuming project is
guaranteed to have. A caller who previously relied on the removed guard to fail fast on a genuine
non-nullable-`T`-carrying-`null` bug — via `!` suppression, or a nullable-disabled or
warnings-not-errors context — now gets a success result carrying `null` instead of an exception at the
point of the bug.

Two new methods make the resulting "success-carrying-null" state usable without re-deriving the same
`IsSuccess` check everywhere:

- **`GetValueOrDefault()`** and **`GetValueOrDefault(T fallback)`** return the success value —
  including a legitimate `null` — or `default`/`fallback` on failure. Neither can distinguish "failed"
  from "succeeded with null"; both read the same.
- **`TryGetValue(out T? value)`** can distinguish them: returns `true` with the (possibly-null)
  success value, or `false` with `default`, mirroring the BCL `Dictionary.TryGetValue` convention.

## Fixed: several silently-inert options across the compiler now do what they always claimed to

Same defect shape as the ODBC and dependency-enforcement fixes above — recurring across the codebase:
a fluent-API input was accepted, stored, and validated, but nothing on the compile or runtime side
ever read it, so setting it had no observable effect and no warning ever said so. Each of the
following now works as documented:

- **`MergeModuleBuilder.Dependency(id)`** — `MsmCompiler` never emitted the standard `ModuleDependency`
  table, so every declared merge-module dependency was silently dropped from the compiled `.msm`. The
  table is now emitted; `RequiredID` carries the declared identifier verbatim, `RequiredLanguage`
  defaults to the declaring module's own language (same-language dependency assumed), and
  `RequiredVersion` is left unconstrained — there is no overload yet to express a cross-language or
  version-pinned dependency.
- **`TransformBuilder.SetProperty(name, value)`** — `TransformCompiler.Compile` validated the model but
  never read `PropertyChanges` when generating the transform, so property changes an author declared
  never appeared in the compiled `.mst`. They are now applied. **New build-time error `MST003`:** a
  `PropertyChanges` key must now be a legal PUBLIC MSI property identifier (`[A-Z_][A-Z0-9_.]*`,
  all-uppercase) — a `.SetProperty(...)` call that previously built and silently did nothing can now
  fail the build if the name could never have worked as a public property anyway.
- **`MsiCompiler(IFileSystem)`** — the constructor overload that exists specifically so tests and
  callers can inject a virtual filesystem was accepted, but `MsiAuthoring.Compile`'s forwarder always
  built its own real `WindowsFileSystem` and ignored the constructor-supplied one. The injected
  instance is now actually used.
- **Four MSIX inputs — `MsixBundleModel.Publisher`, `MsixBuilder.Scope`/`MsixModel.Scope`, and
  `MsixModel.Shortcuts` — are removed rather than silently accepted, and the `MsixExtension`
  category-string API is deleted outright and replaced with real, working capability.**
  `IAppxBundleWriter` derives bundle identity's `Name`/`Publisher` from the payload packages themselves
  and never reads a caller-supplied `Publisher`. `MsixBuilder.Extension(category, entryPoint)` is
  gone — `AppxManifestGenerator` emitted no `<Extensions>` element at all, so a category string could
  never have registered a file type association or protocol handler on a real machine, no matter what
  an author configured. The replacement, `MsixApplicationBuilder.FileTypeAssociation(...)` /
  `.Protocol(...)`, now genuinely emits `uap:Extension`/`uap:FileTypeAssociation`/`uap:Protocol`
  rows — this is a real new capability, not just a rename, since the old API never worked at all. An
  unsupported file-type-association or protocol shape is now a build error
  (`MSIX013`/`MSIX014`/`MSIX015`, all three new this release) instead of a silent no-op.
  `MsixModel.SbomOptions` is wired rather than removed: `MsixBuilder.Sbom()` now writes an opt-in
  CycloneDX 1.6 sidecar (a new `<output>.msix.cdx.json` artifact) the same way the MSI and bundle
  compilers already do; unlike `MsiCompiler`, `MsixCompiler` has no logger, so a requested-but-
  unwritten SBOM fails the compile instead of silently disappearing. **This is source-breaking** — see
  Breaking changes below.
- **`MSIX013`/`MSIX014`/`MSIX015` reject association and protocol names MakeAppx or the Store would
  later reject, at authoring time instead.** All three codes are new this release — file type
  association and protocol registration is itself new this release (see above), so there is no prior
  released version where these checks existed in a weaker form. `MSIX013` catches an invalid file type
  association name (must be lowercase alphanumerics, `.`, `-`, `_`). `MSIX014` fails a file type
  association over 64 characters, with a second `.` after the leading one, or containing a reserved
  character (`< > : % " / \ | ? *`), instead of only failing opaquely at packaging or deployment time.
  `MSIX015` bound-checks protocol names to the 2–39 character range the AppX schema requires, not just
  lowercase. (Within this same beta.6 cycle, `MSIX014`/`MSIX015`'s bound checks were themselves tightened
  once before landing here — an intra-branch refinement, not a change from any shipped behavior.)

None of these change output for a caller who never used the affected input — a `.Dependency(...)`,
`.SetProperty(...)`, or constructor-injected filesystem call that previously had no effect now has one.

## Breaking changes

- **`SbomOptions`/`Integrity()`'s default `SbomFormat` changed from `Spdx` to `CycloneDx`.** `SbomFormat`
  now genuinely selects which document gets generated (see the SBOM/integrity fix above) — previously
  the writer was hardcoded to CycloneDX regardless of the setting, so `Spdx` as the enum's default was
  never load-bearing. Leaving it as the default under the new, honored behavior would have made an
  ordinary `Integrity()` build start emitting SPDX bytes where it has always shipped CycloneDX, and SPDX
  can fail to generate in cases CycloneDX cannot (a file component added without a SHA-1, required by
  SPDX 2.3 §8.4). **This changes no output for a caller who never referenced `SbomFormat`** — a default
  `Integrity()` build keeps producing the same CycloneDX bytes it always has. It only matters if you
  explicitly set `SbomFormat = SbomFormat.Spdx` (or left it unset while relying on the old
  mislabeled-but-CycloneDX output) — the enum's numeric values are unchanged (`Spdx` is still `0`), only
  which one is *chosen by default* moved. **Migration:** if you need CycloneDX, no change is required;
  if you need SPDX, set `SbomFormat = SbomFormat.Spdx` explicitly (this now produces genuine SPDX bytes
  for the first time) and ensure every file component supplies a SHA-1.
- **Removed `IntegritySbomGenerator`, `SbomPackageInfo`, and `SbomFileEntry` from the packable
  `FalkForge.Core` public surface.** Superseded by the format-driven generator described above; no
  caller could construct a correct document from these types without also duplicating the format
  dispatch that now lives centrally. **Migration:** there is no drop-in replacement type — go through
  `SbomOptions`/`IntegrityConfiguration` on `PackageBuilder`/`BundleBuilder` instead of constructing an
  SBOM document directly.
- **`DialogCustomization.SuppressDialog` is now `[Obsolete(error: true)]`** — it compiled, ran, and
  populated `DialogCustomizationModel.SuppressedDialogs`, but `DialogComposer` never read the set, so
  calling it never suppressed anything; it is gated rather than deleted so the compile error names the
  API directly instead of a generic "member not found." **This changes no runtime behavior for any
  existing caller** — suppression never worked — **but it is source-breaking**: any existing
  `.SuppressDialog(...)` call site no longer compiles. **Migration:** delete the call; there is no
  working replacement for dialog suppression in this release (see task #44 in the project backlog for
  status — the `[Obsolete]` message on `SuppressDialog` itself names the same task number).
- **Four unhonored MSIX inputs removed, and the category-string extension API deleted outright.**
  `MsixBundleModel.Publisher` is removed (`IAppxBundleWriter` derives bundle identity from the payload
  packages, never from a caller-supplied publisher, so the setting had nowhere to go);
  `MsixBuilder.Scope`/`MsixModel.Scope` is removed (an MSIX package is always staged and registered
  per-user — provisioning it for every user is a deployment-time act with no manifest representation);
  `MsixModel.Shortcuts` is removed (`AppxManifest` has no shortcut element — Start menu entries come
  from `Applications/Application` + `VisualElements`). Separately, `MsixBuilder.Extension(category,
  entryPoint)` — and the `MsixExtension` type it stored into — is **deleted, not narrowed**:
  `AppxManifestGenerator` emitted no `<Extensions>` element at all for it, so no category string ever
  registered a file type association or protocol handler on a real machine. **This changes no output
  for any existing caller who received real behavior from these inputs, because none of them ever
  did** — but it is source-breaking for any caller referencing the removed members. **Migration:**
  delete references to the removed `Publisher`/`Scope`/`Shortcuts` properties. For file type
  associations and protocol handlers, there is no narrower category to pick — replace the deleted
  `.Extension(category, ...)` call with `MsixApplicationBuilder.FileTypeAssociation(name, fileTypes)` /
  `.Protocol(name)`, the schema-correct per-application APIs that now actually emit the `<Extensions>`
  element; an unsupported file type or protocol shape now fails the build
  (`MSIX013`/`MSIX014`/`MSIX015`) instead of shipping silently unregistered.

- **`IRegistry` gained four new abstract members** (`TryReadSubKeyNames`, `TryGetStringValue`,
  `TryValueExists`, `TryKeyExists` — ten members total, up from six in beta.5) in `FalkForge.Platform`,
  a packable assembly and an explicit injection seam. **This is source-breaking for any external
  implementer of `IRegistry`** — a type outside FalkForge that implements the interface directly (not
  through the shipped `WindowsRegistry`/`MockRegistry`) will no longer compile until it adds the four
  new members. **Migration:** implement the four `Try*` members; each mirrors its non-`Try` sibling but
  returns a `Result<T>` that reports a read failure (e.g. `SecurityException`,
  `UnauthorizedAccessException`) instead of letting it escape uncaught, and treats "not found" as
  success rather than failure — see the xmldoc on each member in `IRegistry.cs` for the exact
  fail-closed semantics callers should rely on.

- **Removed the unwired parallel-cabinet feature: `ParallelCabinetBuilder`, `CabinetWorkItem`,
  `CabinetBuildResult`, `PackageBuilder.CabinetThreads(int)`, and
  `PackageModel.CabinetThreadCount`.** These shipped in `0.5.0-beta.1` through `beta.5` but were
  two halves of a feature that was never finished: `ParallelCabinetBuilder` had zero production
  callers (real cabinet building always went through the sequential loop in
  `MsiAuthoring.Cabinets.cs`), and `CabinetThreadCount` was accepted and stored by the fluent
  builder but read by nothing — cabinet compression stayed single-threaded no matter what value a
  caller passed to `CabinetThreads(...)`.

  **This changes no runtime behavior for any existing caller, but it is source-breaking.** Because
  `CabinetThreadCount` never had any effect, compression was already single-threaded before this
  change and still is after it — no build's *output* changes. But a build script that calls
  `.CabinetThreads(n)` will no longer compile: the method is gone, not deprecated.

  **Migration:** if your build script calls `.CabinetThreads(n)` on a `PackageBuilder`, delete
  that call. There is no replacement API, parallel or otherwise; nothing else needs to change.

- **Removed the unwired file-sequencing strategy machinery: `FileSequencingStrategy`,
  `FileSequenceEntry`, the (then-still-extant) `MsiRecipeBuildOptions.Sequencing` knob, and
  `MsiDatabaseRecipe.FileSequencing`** (plus the internal `IFileSequencer` / `NoOpFileSequencer`
  pair and the `RecipeBuildContext.FileSequencer` slot). This is the same shape of unfinished
  feature as the parallel-cabinet removal above: `IFileSequencer.Sequence(...)` was never called
  from anywhere, `Sequencing` was accepted and stored but read by nothing, and `MsiRecipeBuilder`
  unconditionally emitted `FileSequencing = ImmutableArray<...>.Empty`. Real File-table sequence
  numbers are — and always were — assigned by `FileTableProducer` from the ordinal index of the
  resolved file list. (`MsiRecipeBuildOptions` itself, and the `Sequencing` knob with it, was
  removed entirely in a later beta.6 commit — see below.)

  **This changes no MSI output for any existing caller, but it is source-breaking.** Because
  `Sequencing` never had any effect, file ordering was already ordinal before this change and
  still is after it. But a caller that constructs an `MsiDatabaseRecipe` literal (which required
  the now-removed `FileSequencing` property) will no longer compile.

  **The recipe content hash changes value.** `RecipeContentHasher` hashed the `FileSequencing`
  array as part of `MsiDatabaseRecipe.ContentHash`. Because the array was always empty, the only
  bytes it ever contributed were the array's own four-byte little-endian element count — a constant
  `00 00 00 00`. Crucially, the old `AppendFileSequencing` wrote that count *before* its
  empty-array early return, so those four zero bytes were fed to SHA-256 on every single build.
  Removing the call therefore removes exactly four bytes from the hash payload, shifting every
  recipe's `ContentHash` to a new — still fully deterministic — value.

  Worked example, for a minimal recipe whose hash payload is otherwise entirely zeroes (no tables,
  no streams, no cabinet embeddings, and an all-empty/zero `SummaryInfoRecipe`). The old hasher fed
  64 zero bytes and the new one feeds 60:

  | | Bytes hashed | `ContentHash` |
  |---|---|---|
  | Before | 64 | `f5a5fd42d16a20302798ef6ed309979b43003d2320d9f0e8ea9831a92759fb4b` |
  | After | 60 | `5dcc1b5872dd9ff1c234501f1fefda01f664164e1583c3e1bb3dbea47588ab31` |

  This was a deliberate choice: the field hashed nothing real, and no golden test, on-disk cache, or
  published artifact pins a literal recipe content hash.

  **Migration:** delete any `Sequencing = ...` initializer; delete any `FileSequencing = ...`
  initializer from an `MsiDatabaseRecipe` construction. There is no replacement API — file
  sequencing is not configurable, and was not configurable before this change either.

- **Removed `FeatureStateExtensions.GetInstallStatus(this FeatureState, InstallState)` and the
  `FeatureInstallStatus` enum from `FalkForge.Ui.Abstractions`.** The extension method had no
  callers anywhere — not in the shipped WPF UI, not in Studio, not in tests — and the enum existed
  only as its return type. Neither participated in any install, detect, or UI code path, so no
  behavior changes.

  **Migration:** there is no replacement. A caller that mapped a `FeatureState` plus a bundle-level
  `InstallState` to a display status was reimplementing a helper nothing else used; the underlying
  `FeatureState` and `InstallState` types are unchanged and still public, so the same two-line
  mapping can be written locally if it is genuinely needed.

- **Removed `MsiRecipeBuildOptions` entirely**, along with the `options` parameter on
  `MsiRecipeBuilder.Build` (both overloads) and `BuildCore`, and the `RecipeBuildContext.Options`
  passthrough. By the time of this removal the record's only two knobs, `EagerStreamHashing` and
  `MaxInMemoryStreamBytes`, were both accepted and stored but read by nothing: no producer ever
  consumed either one. Each producer already picks its stream's `StreamSource` statically, fixed by
  what it emits, never by size: `BinaryTableProducer`, `IconTableProducer`, and the cabinet builder
  in `MsiAuthoring.Cabinets` register `StreamSource.FilePath` unconditionally, while
  `ExtensionTableEmitter` and `CustomTablesProducer` register `StreamSource.InMemory`
  unconditionally. No producer ever compared a size against `MaxInMemoryStreamBytes`, so the knob
  could not influence anything. This is the same shape of unfinished feature as the other entries in
  this section — a knob bag with no reader.

  **This changes no MSI output for any existing caller, but it is source-breaking.** Because
  neither knob ever had an effect, each producer's `StreamSource` choice was already fixed before
  this change and still is after it. But a caller that passes an `MsiRecipeBuildOptions` argument to
  `MsiRecipeBuilder.Build`, or that constructs `new MsiRecipeBuildOptions { ... }` at all, will no
  longer compile — the type is gone, not deprecated.

  **Migration:** delete the `options` argument from any `MsiRecipeBuilder.Build(...)` call; delete
  any `MsiRecipeBuildOptions` construction. There is no replacement API. A real options type will
  be re-added when there is a real knob to put in it.

- **Removed `PipelineContext.SilentMode`, `IsPlanOnly`, and `PlanOnlyOutputPath`.** All three were
  dead: nothing in production could ever set them (`InstallerPipelineBuilder.WithSilentMode` and
  `WithPlanOnlyMode` were referenced in `PipelineContext`'s own xmldoc but never existed, and
  `PipelineContext` itself is internal), so no shipped build was ever affected by any of this.

  `SilentMode` specifically was worse than merely unwired — its licence-gate branch in `PlanStep`
  was wrong by design, not just incomplete. When set, it made the licence check skip entirely:
  `request.LicenseAccepted == false` — an explicit, deliberate DECLINE — would have proceeded
  anyway, logging `"Silent mode: license auto-accepted"` regardless of what the caller actually
  passed. It conflated "no UI is present" with "consent was given," which are not the same thing.
  Again: no shipped build could reach this branch, because nothing ever constructed a
  `PipelineContext` with `SilentMode = true` outside of the type's own now-deleted unit tests — so
  this is a design-correctness removal, not a fix for something that misbehaved for any real
  install.

  **This changes no runtime behavior for any existing caller** — there was no way to reach any of
  the three members from outside `FalkForge.Engine` — **but it is source-breaking** for anything
  that referenced them directly (only the type's own now-deleted tests did).

  **Migration:** there is no replacement. Proper headless/silent install support is planned for a
  later beta and will require an explicit, separate accept flag for licence consent — silent mode
  will never again be allowed to imply acceptance.

## Hardening

- **`SetExternalUI`'s native-facing callback delegate is now rooted for the process lifetime.**
  `MsiSetExternalUIW` registers a process-global callback Windows Installer can invoke at any point
  while the process runs, but `[LibraryImport]` only keeps the marshalled delegate alive for the
  duration of the P/Invoke call that registers it — once that call returns, nothing else referenced
  the delegate, so a garbage collection could reclaim it while Windows Installer still held the native
  function pointer, making the next invocation call into freed memory. Any FalkForge-based installer
  using `WindowsMsiApi.SetExternalUI` for custom UI was exposed. The delegate is now rooted for the
  life of the process; a regression test pins that the reflected field actually holds the delegate
  after the call returns.

- **PE header bounds check widened to 64-bit so it cannot be bypassed by integer overflow.** The
  `e_lfanew` range guard in `WixBurnAccess.Open` (the bundle decompiler's PE parser, which reads a
  foreign, potentially attacker-controlled executable during `forge migrate`/decompilation) computed
  `eLfanew + 4 > stream.Length` in unchecked `Int32` arithmetic. `e_lfanew` is read directly from the
  file's own PE header, so a value near `Int32.MaxValue` wrapped the addition to a negative number,
  defeating the guard. The malformed offset still failed safely downstream (an out-of-range
  `BinaryReader` read triggered the existing catch-all rejection), so this was not an exploitable
  bypass in the shipped code path — but it was defeating its own explicit check by accident, and a
  future refactor narrowing that catch-all could have turned it into a real one. The comparison now
  widens to `long` and rejects on its own terms.

- **Canonical MSI-SQL identifier grammar, and an exact-anchor sweep across every identifier guard
  that feeds it.** Every table/column identifier FalkForge either authors (recipe emission,
  custom tables, extension-contributed tables, execution-step action IDs) or reads back out of a
  real MSI (`MsiTableReader`, `MsiTableAccess`) is now validated by one shared grammar,
  `FalkForge.MsiIdentifierGrammar` (`IsValidForWrite` / `IsValidForRead`), instead of each call site
  restating its own regex. This closes a gap where the write side (`TableId`) had already moved to
  the canonical grammar but five sibling guards had not: `RecipeColumn`, `CustomTableBuilder`,
  `ExtensionTableEmitter`, `CustomTablesProducer.cs`, and `ExecutionStepEmitter`.

  As part of the same sweep, every one of those guards moved off a `^...$`-anchored regex onto
  `\A...\z`. In .NET, `$` matches end-of-string OR immediately before a single trailing `\n` even
  without `RegexOptions.Multiline`, so an otherwise-invalid identifier with a trailing newline
  (e.g. `"Property\n"`) previously slipped past the anchor undetected. Input that relied on this
  quirk and previously passed silently — a table name, column name, or execution-step action ID
  ending in a single trailing newline — is now correctly rejected.

  **For the `ProcessRunner` / command-line paths, this is a hardening / defense-in-depth change,
  not a fix for an exploitable vulnerability.** The write-side identifiers this sweep covers (table
  names, column names, execution-step action IDs) end up on a command line via `ProcessRunner`,
  which runs with `UseShellExecute = false` (no shell, so shell metacharacters are inert), and the
  Windows argv tokenizer splits arguments on space and tab only — never on `\n`. The anchor quirk
  permits at most one trailing newline at the very end of the string, so it could never be used to
  inject content mid-string; everything after it in a real attack string would already be
  truncated by the character-class check that precedes the anchor. The practical effect of the fix
  on this path is exact-anchor correctness and a single canonical grammar, not the closure of an
  exploitable hole. **This reasoning is specific to the argv sink and does not transfer to the
  MSI-SQL identifier paths below — those are a different sink with their own, separately-argued
  safety case.**

- **`MsiTableReader` (Studio's MSI inspector) and `MsiTableAccess` (`FalkForge.Decompiler`)
  validation guards.** `MsiTableReader.ReadTable` validates a caller-supplied table name against
  the read-side grammar before it is interpolated into MSI-SQL — the one path in FalkForge that can
  receive a genuinely untrusted identifier (echoed back from a real, possibly hand-crafted MSI's
  own `_Tables` catalog) rather than a compile-time-constant schema name. A malformed `_Columns`
  query failure is now propagated as a real error instead of being silently treated as "table has
  no columns."

  **These MSI-SQL paths have no known exploit; the identifier check is defense-in-depth, for
  reasons distinct from the `ProcessRunner` case above:**
  - The grammar itself (`IsValidForRead`: a letter or underscore, then letters, digits, underscores,
    or dots) is an allow-list containing no quote, semicolon, or comment-delimiter character — so
    even if an identifier were interpolated unquoted, there is no character available to break out
    of either a backtick-quoted identifier or a single-quoted string literal.
  - Table/column identifiers are interpolated as backtick-quoted MSI-SQL identifiers (e.g.
    `` SELECT `Name` FROM `_Columns` `` — see `MsiTableReader.ReadTable`); the one place a validated
    name is instead compared as a single-quoted string value (the `_Columns` lookup's
    `` WHERE `Table` = '...' `` clause) is equally safe because the same quote-free allow-list
    already applies to it.
  - Every query in this codebase runs through `MsiDatabaseOpenView` / `MsiViewExecute`
    (`MsiDatabase.QueryRows`), which accepts and executes exactly one Windows Installer SQL
    statement per call. The Windows Installer SQL grammar has no comment syntax (`--`, `/* */`) and
    no semicolon-separated statement batching — there is no way to smuggle a second statement or
    comment out a trailing clause through this API even before considering the identifier grammar.
  - Both `MsiTableReader.ReadTable` and `MsiTableAccess.Open` open the database via
    `MsiDatabase.Open(msiPath, readOnly: true)` — genuinely read-only at the Windows Installer API
    level, not just by convention.

- Two identifier-format regexes (`FirewallRules` port validation, the assembly-version format
  check in `RemainingRules`) switched from `\d` to `[0-9]`. `\d` is Unicode-aware in .NET and
  matches non-ASCII decimal digits (e.g. Arabic-Indic `١٢٣`); the firewall port check would
  previously let such input reach `int.Parse` and throw an unhandled `FormatException` instead of
  reporting a normal validation error. Author-controlled, build-time input only — a robustness fix,
  not a runtime security exposure.

## Packaging

- **XML doc files now ship in every packable nupkg**, giving IntelliSense for FalkForge's public API
  for the first time. `GenerateDocumentationFile` was previously set in no `src` `.csproj`, so the
  ~4,000 missing-XML-comment diagnostics across the solution could not even be measured. They are now
  tiered to `suggestion` severity (visible, trackable, never silently suppressed) rather than promoted
  to build errors — thousands of comments is not a one-pass fix.

## Known limitations / in progress

- **A registry-value pre-UI prerequisite condition against an ACL-restricted path can crash before the
  WPF UI even exists.** `SearchConditionEvaluator` calls the bare `IRegistry.KeyExists`/
  `GetStringValue` (not their fail-closed `Try*` siblings) when evaluating a
  `SearchConditionType.RegistryValue` condition. Neither has a try/catch in `WindowsRegistry` — unlike
  their `Try*` siblings, which exist specifically because the bare calls let an access-denied exception
  escape uncaught (see the xmldoc on `IRegistry.TryKeyExists`). An author who declares a pre-UI
  prerequisite with `SearchConditionType.RegistryValue` against a path the current user cannot read
  gets a `SecurityException` escaping through `PreUIPrerequisiteDetector.IsInstalled` and out of the
  NativeAOT bootstrapper before the WPF UI exists — a raw crash with no dialog, not a graceful
  "prerequisite not found." This same release migrated `BuiltInVariables.PopulateRebootPending` off
  the equivalent bare `KeyExists` call for exactly this reason (see above); the same fix was not
  applied to `SearchConditionEvaluator`. Not fixed in this release — tracked separately, and not a
  regression (the bare calls predate this beta).
- **The live paths (real bundle install/rollback, IIS apply, feature-picker `ADDLOCAL`, external-
  container network download, turnkey UI, per-culture install UI) are built and unit-proven but
  only exercised end-to-end under `FALKFORGE_REAL_SYSTEM_E2E=1`** on a real, elevated machine — see
  `docs/testing/real-machine-verification.md` for the runbook. None of these run in CI.
- **MSIX build is not available via `forge build` or the MSBuild SDK** — it's script-only today,
  via `InstallerMsix.BuildMsix()` / `InstallerMsix.BuildMsixBundle()` called directly from a build
  script.
- **Mutation-testing scores are directional, not authoritative.** The two `coverage-analysis` modes
  Stryker can run under this repo's MTP-based test runner — `perTest` and `off` — disagree by up to
  ~25 percentage points on identical code, and the upstream MTP runner itself is still preview.
  Treat any mutation score in `docs/testing/mutation-testing.md` as a lead to investigate by hand
  (reproduce the mutation, run the affected tests, confirm a failure), not as a quality gate or a
  number to cite on its own.
- **Engine log redaction covers structured properties only** — free-text log messages and
  exception messages are not scanned; a secret interpolated into a message string or surfaced through
  `Exception.Message` (e.g. a `SqlException`'s connection string) is not masked.
