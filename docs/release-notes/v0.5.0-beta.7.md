# FalkForge v0.5.0-beta.7 (unreleased)

This file accumulates fixes landed on `main` since `v0.5.0-beta.6` was tagged. It is not yet cut or
published — no version, packaging, or requirements section below, because none of that has been
decided for this cycle yet. Entries are added as work lands; this note will gain the usual sections
(Breaking changes, Packaging, Requirements) when the release is actually cut.

## Fixed: an author-scheduled action colliding with a baseline standard action now fails with a named diagnostic (SEQ001) instead of a bare duplicate-row error

`v0.5.0-beta.6` warned that hand-scheduling `FindRelatedProducts` — the standard workaround for issue
\#65 before that release fixed it — now collides with the compiler's own baseline row, and that the
collision "fails the build at `PrimaryKeyValidator` ... a build-time validation failure, not a silent
no-op." That was true, but the failure was a generic `Duplicate primary key in table
InstallExecuteSequence: FindRelatedProducts`-style message with no guidance pointing at the actual
cause — exactly the audience least likely to guess it, since they are the people who diagnosed issue
\#65 themselves and are now hitting a *new* error from the *fix* for the bug they already worked around.

`InstallExecuteSequenceTableProducer` and `InstallUISequenceTableProducer` now reject a manually
scheduled action whose name collides with a baseline row before any table row is even produced, with
a diagnostic that names the cause:

```
SEQ001: 'FindRelatedProducts' is scheduled automatically by the compiler and collides with the
InstallExecuteSequence baseline row of the same name. Remove the manual ExecuteSequence(...) entry
for 'FindRelatedProducts' — InstallExecuteSequence's primary key is Action, so scheduling it again
would fail the build with a duplicate-row error.
```

The same guard applies to `InstallUISequence`/`UISequence(...)`, and to any standard action name the
sequence producers themselves schedule — not only `FindRelatedProducts` — so scheduling e.g.
`InstallFiles` or `AppSearch` by name is caught the same way. The check is derived from the exact
baseline row set each producer builds for the package being compiled (not a separately maintained
list), so it cannot drift out of sync with what the producer actually emits.

**This does not cover action names contributed by extensions.** Rows an extension's
`IMsiTableContributor` emits directly into `InstallExecuteSequence`/`InstallUISequence` — for example
the ODBC extension's `InstallODBC`/`RemoveODBC` rows — are merged in after the sequence producers have
already run, so they are outside the baseline snapshot SEQ001 checks against. An author whose manually
scheduled action collides with one of those still hits a build failure, just the generic
duplicate-primary-key error, not SEQ001's named diagnostic.

**This does not affect using a baseline action name as a position anchor.** Scheduling a *different*
action `.After("FindRelatedProducts")` or `.Before("FindRelatedProducts")` — as this repository's own
`demo/09-advanced-msi/Program.cs` does for `SetUpgradeFlag` — still works exactly as documented in the
beta.6 notes; SEQ001 only fires when the author-scheduled action's own name collides with a baseline
row, never when a baseline name is merely referenced as a relative position.

**Migration:** if you hit SEQ001, delete the manual `ExecuteSequence(...)`/`UISequence(...)` entry for
the named action — the compiler now schedules it for you. See &sect;8.14 in `documentation.html` and
`docs/validation-error-codes.md` (SEQ001) for the full detail.

## Fixed: correction to beta.6 — the `Banner` region itself was the bug, not just its docs (issue #67 follow-up)

Beta.6 fixed `BannerBitmap`'s documentation to describe the control's *actual* rendered size (493x77 px)
instead of the stale 493x58 px figure, and explicitly flagged the underlying `Banner` region height (58)
as an open question: *"the classic Windows Installer / WiX banner control is 370x44 DLU, which renders
at 493x58 px ... If the region height is later corrected to 44 DLU, the control's actual rendered size
becomes 493x58 px again and this release's 493x77 figure would need to change right back."*

That open question is now settled: **the region was the bug.** `Layouts.Standard370x270`'s `Banner`
region (`src/FalkForge.Compiler.Msi/UI/Layout/Layouts.cs`) declared `Height = 58` — the banner's classic
*pixel* height — where WiX's own `InstallDirDlg.wxs` gives `BannerBitmap`/`BannerLine` a height of **44**
Installer Units. 58 is precisely WiX's prescribed pixel height for the banner image (493x58 px): a pixel
value had been written into a field the MSI Dialog Table reference explicitly documents as being in
"Installer Units, not dialog units" — a different, easily-conflated concept from Windows dialog units.
`Layouts.cs`'s `Banner.Bounds.Height` is now **44**, matching WiX exactly.

**This changes rendered output for every package that sets `BannerBitmap` or leaves it unset.** The
synthesized (or author-supplied, matched-dimension) banner control now renders at its correct classic
size, **493x58 px**, not the 493x77 px beta.6 documented as current behavior:

- **If you re-authored banner art to 493x77 px following beta.6's guidance**, that art now renders
  squashed to fit the corrected 493x58 px control area. Re-author to **493x58 px** (the size beta.5 and
  earlier's documentation always described, before beta.6's temporary correction to 493x77).
- **If you left your existing 493x58 px banner art unchanged through beta.6** (per that release's advice
  not to re-author before the question was settled), no action is needed — your art already matches the
  corrected size.
- **If you never set `BannerBitmap`**, FalkForge's own synthesized banner control now occupies the
  correct 44-unit region; no author action is needed either way.

`ContentArea` (Y=60), `TitleRow`, `Description`, and the synthesized `HeaderIcon` are all placed with
coordinates independent of the `Banner` region's height — `ContentArea`'s Y=60 origin already matched
WiX's own gap below the corrected 44-unit banner (WiX's `InstallDirDlg.wxs` places its own `BannerLine`
at Y=44 and its first content control, `FolderLabel`, at Y=60), so none of those controls needed to
move once the one wrong field was fixed.

**This release also adds a new control, not just a corrected one.** Every interior wizard-page dialog —
`LicenseAgreementDlg`, `InstallDirDlg`, `CustomizeDlg`, `SetupTypeDlg`, `InstallScopeDlg`, `ProgressDlg`,
and `MsiRMFilesInUse` — now declares a `BannerLine` control: a horizontal `Line` separator at the
`Banner` region's own bottom edge (X=0, Y=44, Width=370, Height=0), matching WiX's own
`InstallDirDlg.wxs` convention of placing a `BannerLine` beneath `BannerBitmap`. This is new geometry,
not part of the Banner-height fix above: it was previously absent from every FalkForge-built dialog and
is now present in the compiled MSI's `Control` table for these seven dialogs. Upgraders who diff a
newly-compiled package's `Control` table against an older one will see this new row in addition to the
banner art resizing described above. `WelcomeDlg` and `ExitDlg` are unaffected — they paint a
full-canvas `DialogBitmap` background instead of a distinct `Banner` strip, so no `BannerLine` is added
to either.

`documentation.html` §14 ("MSI Dialog Templates" → "Dialog Customization API" → "Bitmap Dimensions and
Text Safe Zones") is updated to match: every pixel figure in that section has been re-derived from the
corrected 44-unit `Banner` region. The `Description`/`HeaderIcon` safe-zone conclusions (roughly x
33-406 and x 461-482 px, respectively, leaving a ~55px clear strip at x 406-461) are unchanged — those
placements are absolute coordinates independent of the banner's height, so only the banner's own
vertical extent (77 → 58 px) moves. `docs/dialog-template-architecture.md`'s region table is corrected
to match as well.

**Terminology fix, same root cause:** `DialogCustomizationModel`/`DialogCustomization`'s xmldoc, and the
above `documentation.html` section, previously called these coordinates "DLU" / "dialog units"
throughout. The MSI Dialog Table reference is explicit that `Dialog`/`Control` table `Width`/`Height`
values are in **Installer Units**, not Windows dialog units — a different, if confusable, concept. An
Installer Unit is approximately 1/12 the height of the 10-point MS Sans Serif font; the 4/3
Installer-Unit-to-pixel figure used throughout this documentation is only an approximation of that
ratio at typical rendering, not an exact defined conversion. Using the wrong term did not itself cause
the rendering bug above, but conflating "Installer Unit" with "Windows dialog unit" is the same kind of
mixing-up-of-units mistake, and is corrected everywhere the bitmap sizing is described.

Found by comparing `Layouts.cs` directly against WiX's own `WelcomeDlg.wxs`/`InstallDirDlg.wxs` sources
— the `Banner` region diverges from WiX's own convention only on this one field. Every other stock
region (`TitleRow`, `ContentArea`, `BottomLine`, `ButtonRow`) and the Welcome/Exit `DialogBitmap` region
already matched WiX on Y and height; two smaller, pre-existing deltas remain, unrelated to this fix:
`BottomLine`'s Width is **370** (`Layouts.cs`) against WiX's **373**, and `ButtonRow`'s non-rightmost
buttons sit 4 DLU left of WiX's positions on `InstallScopeDlg`/`SetupTypeDlg` (documented in
`InstallScopeDlgBuilder.cs:22` and `SetupTypeDlgBuilder.cs:14` as the phase-6 ButtonRow geometry
deviation) — the rightmost button (Cancel) still lands exactly on WiX's X in every case.
