# FalkForge v0.5.0-beta.7 (unreleased)

This file accumulates fixes landed on `main` since `v0.5.0-beta.6` was tagged. It is not yet cut or
published — no version, packaging, or requirements section below, because none of that has been
decided for this cycle yet. Entries are added as work lands; this note will gain the usual sections
(Breaking changes, Packaging, Requirements) when the release is actually cut.

## Fixed: `BuiltInPrerequisites.NetFx472()` reported "not installed" on every machine, including machines that have it, because its detection compared a REG_DWORD value with a string-only registry read

`NetFx472()`'s search condition compares `HKLM\SOFTWARE\Microsoft\NET Framework Setup\NDP\v4\Full\Release
>= 461808`. `Release` is a REG_DWORD on every real machine, never a REG_SZ. `SearchConditionEvaluator`'s
comparison path read it with a string-only accessor, whose contract is that a value which exists but is
not string-typed comes back as SUCCESS with `null` — indistinguishable from the value being absent. The
comparison therefore always saw `null` and reported "not installed", regardless of what .NET Framework
version was actually on the machine.

This was worse than a no-op detection check. `NetFx472()` is a **chain** package (`.ExePackage(...)`
inside a `PackageGroupModel`), not a `PreUIPackages` entry — it never goes through
`PreUIBootstrapOrchestrator`/`PreUIPrerequisiteInstaller` at all, so a prior draft of this note that
attributed an unexpected UAC prompt to this bug was wrong. (The UAC-elevation risk from a misdetected
prerequisite is real, but it belongs to `BuiltInPrerequisites.DotNet10DesktopAsPreUI()` — the one
built-in that *does* run on the pre-UI path — and that prerequisite has its own, different detection
defect not fixed by this branch; see "Found during the sweep but explicitly out of scope" below.) The
actual consequence here: every `Vital` prerequisite reported missing is planned for (re)install on
every single run, including on a machine that already has it — `Planner`'s "skip prerequisites already
installed" ordering never sees a match. `PackageExecutor.MapExitCode` fails the package when the redist
process exits non-zero, which redist installers commonly do when invoked against a machine that already
has them — and `ApplyStep` aborts the *entire* chain on the first package failure. A package built with
this built-in could run a redundant, silent redist reinstall on every launch and, on a machine where that
reinstall happens to exit non-zero, abort the whole install/update with no further UI and no message.

`SearchConditionEvaluator.EvaluateRegistryComparison` now falls back to a numeric (REG_DWORD) read when
the string read comes back `null`, before concluding the value is absent — a new
`IRegistry.TryGetDWordValue` mirrors the existing `TryGetStringValue` contract (SUCCESS with `null` for
absent/wrong-type, `Failure` only for a genuine read error such as access denied). A read failure on
either the string or the numeric read still propagates as a `Failure`, exactly as before — it is never
folded into "absent". If a REG_DWORD value is found but the author's comparison literal cannot be parsed
as an integer, evaluation now fails loudly (a `DetectionError`) instead of silently comparing as
"not equal" forever.

The sibling `"exists"` comparison path (`EvaluateRegistryExists`) had the identical type-blindness — it
also used the string-only accessor, so `RegistryExists(root, key, valueName)` against a REG_DWORD value
name likewise always reported "absent". It now uses the already-existing, type-agnostic
`IRegistry.TryValueExists` instead, which also makes it fail-closed on a genuine read error (the old bare
accessor let a `WindowsRegistry` read failure escape as an unhandled exception instead of reporting it).

**Also affected, now fixed by the same evaluator change (no separate code change needed):**
`BuiltInPrerequisites.VCRedist14x64()`'s `Installed = 1` check — `Installed` is a REG_DWORD too.

**Found during the sweep but explicitly out of scope for this fix:**
`BuiltInPrerequisites.DotNet10DesktopAsPreUI()`'s search condition compares the *value's data* for
equality (`"10.0.0" = "10.0.0"`) against `HKLM\SOFTWARE\dotnet\Setup\InstalledVersions\x64\sharedfx\
Microsoft.WindowsDesktop.App`. On a real machine, an installed .NET Desktop Runtime version appears as a
**value name** under that key (e.g. a value named `10.0.0`), not as string data equal to the version — the
real value data is typically a REG_DWORD placeholder, not the version string. This is a different defect
shape (wrong search-condition semantics — an equality check where an existence check on the value name was
intended — not a string/numeric type-read mismatch), was not fixed by the string-or-numeric fallback above
(a REG_DWORD placeholder still would not equal a non-numeric literal), and needs its own targeted fix and
tests. Since this prerequisite runs pre-UI and can block the WPF installer UI from ever starting, it is
flagged here as a priority follow-up rather than folded into this change.

REG_QWORD, REG_BINARY, and REG_MULTI_SZ registry values still read as `null` through the string path and
are **not** covered by the new numeric fallback — no built-in prerequisite or documented search condition
compares against one today, and typed reads for those kinds do not exist elsewhere in `IRegistry` either,
so adding them was judged out of scope for this fix.

## Fixed: an author-scheduled action colliding with a baseline standard action now fails with a named diagnostic (SEQ001) instead of a bare duplicate-row error

`v0.5.0-beta.6` warned that hand-scheduling `FindRelatedProducts` — the standard workaround for issue
\#65 before that release fixed it — now collides with the compiler's own baseline row, and that the
collision "fails the build at `PrimaryKeyValidator` ... a build-time validation failure, not a silent
no-op." That was true, but the failure was a generic `Duplicate primary key in table
InstallExecuteSequence: FindRelatedProducts`-style message with no guidance pointing at the actual
cause — exactly the audience least likely to guess it, since they are the people who diagnosed issue
\#65 themselves and are now hitting a *new* error from the *fix* for the bug they already worked around.

`InstallExecuteSequenceTableProducer` and `InstallUISequenceTableProducer` now reject a manually
scheduled action whose name collides with a baseline row before any table row is even produced, with
a diagnostic that names the cause:

```
SEQ001: 'FindRelatedProducts' is scheduled automatically by the compiler and collides with the
InstallExecuteSequence baseline row of the same name. Remove the manual ExecuteSequence(...) entry
for 'FindRelatedProducts' — InstallExecuteSequence's primary key is Action, so scheduling it again
would fail the build with a duplicate-row error.
```

The same guard applies to `InstallUISequence`/`UISequence(...)`, and to any standard action name the
sequence producers themselves schedule — not only `FindRelatedProducts` — so scheduling e.g.
`InstallFiles` or `AppSearch` by name is caught the same way. The check is derived from the exact
baseline row set each producer builds for the package being compiled (not a separately maintained
list), so it cannot drift out of sync with what the producer actually emits.

**This does not cover action names contributed by extensions.** Rows an extension's
`IMsiTableContributor` emits directly into `InstallExecuteSequence`/`InstallUISequence` — for example
the ODBC extension's `InstallODBC`/`RemoveODBC` rows — are merged in after the sequence producers have
already run, so they are outside the baseline snapshot SEQ001 checks against. An author whose manually
scheduled action collides with one of those still hits a build failure, just the generic
duplicate-primary-key error, not SEQ001's named diagnostic.

**This does not affect using a baseline action name as a position anchor.** Scheduling a *different*
action `.After("FindRelatedProducts")` or `.Before("FindRelatedProducts")` — as this repository's own
`demo/09-advanced-msi/Program.cs` does for `SetUpgradeFlag` — still works exactly as documented in the
beta.6 notes; SEQ001 only fires when the author-scheduled action's own name collides with a baseline
row, never when a baseline name is merely referenced as a relative position.

**Migration:** if you hit SEQ001, delete the manual `ExecuteSequence(...)`/`UISequence(...)` entry for
the named action — the compiler now schedules it for you. See &sect;8.14 in `documentation.html` and
`docs/validation-error-codes.md` (SEQ001) for the full detail.

## Fixed: correction to beta.6 — the `Banner` region itself was the bug, not just its docs (issue #67 follow-up)

Beta.6 fixed `BannerBitmap`'s documentation to describe the control's *actual* rendered size (493x77 px)
instead of the stale 493x58 px figure, and explicitly flagged the underlying `Banner` region height (58)
as an open question: *"the classic Windows Installer / WiX banner control is 370x44 DLU, which renders
at 493x58 px ... If the region height is later corrected to 44 DLU, the control's actual rendered size
becomes 493x58 px again and this release's 493x77 figure would need to change right back."*

That open question is now settled: **the region was the bug.** `Layouts.Standard370x270`'s `Banner`
region (`src/FalkForge.Compiler.Msi/UI/Layout/Layouts.cs`) declared `Height = 58` — the banner's classic
*pixel* height — where WiX's own `InstallDirDlg.wxs` gives `BannerBitmap`/`BannerLine` a height of **44**
Installer Units. 58 is precisely WiX's prescribed pixel height for the banner image (493x58 px): a pixel
value had been written into a field the MSI Dialog Table reference explicitly documents as being in
"Installer Units, not dialog units" — a different, easily-conflated concept from Windows dialog units.
`Layouts.cs`'s `Banner.Bounds.Height` is now **44**, matching WiX exactly.

**This changes rendered output for every package that sets `BannerBitmap` or leaves it unset.** The
synthesized (or author-supplied, matched-dimension) banner control now renders at its correct classic
size, **493x58 px**, not the 493x77 px beta.6 documented as current behavior:

- **If you re-authored banner art to 493x77 px following beta.6's guidance**, that art now renders
  squashed to fit the corrected 493x58 px control area. Re-author to **493x58 px** (the size beta.5 and
  earlier's documentation always described, before beta.6's temporary correction to 493x77).
- **If you left your existing 493x58 px banner art unchanged through beta.6** (per that release's advice
  not to re-author before the question was settled), no action is needed — your art already matches the
  corrected size.
- **If you never set `BannerBitmap`**, FalkForge's own synthesized banner control now occupies the
  correct 44-unit region; no author action is needed either way.

`ContentArea` (Y=60), `TitleRow`, `Description`, and the synthesized `HeaderIcon` are all placed with
coordinates independent of the `Banner` region's height — `ContentArea`'s Y=60 origin already matched
WiX's own gap below the corrected 44-unit banner (WiX's `InstallDirDlg.wxs` places its own `BannerLine`
at Y=44 and its first content control, `FolderLabel`, at Y=60), so none of those controls needed to
move once the one wrong field was fixed.

**This release also adds a new control, not just a corrected one.** Every interior wizard-page dialog —
`LicenseAgreementDlg`, `InstallDirDlg`, `CustomizeDlg`, `SetupTypeDlg`, `InstallScopeDlg`, `ProgressDlg`,
and `MsiRMFilesInUse` — now declares a `BannerLine` control: a horizontal `Line` separator at the
`Banner` region's own bottom edge (X=0, Y=44, Width=370, Height=0), matching WiX's own
`InstallDirDlg.wxs` convention of placing a `BannerLine` beneath `BannerBitmap`. This is new geometry,
not part of the Banner-height fix above: it was previously absent from every FalkForge-built dialog and
is now present in the compiled MSI's `Control` table for these seven dialogs. Upgraders who diff a
newly-compiled package's `Control` table against an older one will see this new row in addition to the
banner art resizing described above. `WelcomeDlg` and `ExitDlg` are unaffected — they paint a
full-canvas `DialogBitmap` background instead of a distinct `Banner` strip, so no `BannerLine` is added
to either.

`documentation.html` §14 ("MSI Dialog Templates" → "Dialog Customization API" → "Bitmap Dimensions and
Text Safe Zones") is updated to match: every pixel figure in that section has been re-derived from the
corrected 44-unit `Banner` region. The `Description`/`HeaderIcon` safe-zone conclusions (roughly x
33-406 and x 461-482 px, respectively, leaving a ~55px clear strip at x 406-461) are unchanged — those
placements are absolute coordinates independent of the banner's height, so only the banner's own
vertical extent (77 → 58 px) moves. `docs/dialog-template-architecture.md`'s region table is corrected
to match as well.

**Terminology fix, same root cause:** `DialogCustomizationModel`/`DialogCustomization`'s xmldoc, and the
above `documentation.html` section, previously called these coordinates "DLU" / "dialog units"
throughout. The MSI Dialog Table reference is explicit that `Dialog`/`Control` table `Width`/`Height`
values are in **Installer Units**, not Windows dialog units — a different, if confusable, concept. An
Installer Unit is approximately 1/12 the height of the 10-point MS Sans Serif font; the 4/3
Installer-Unit-to-pixel figure used throughout this documentation is only an approximation of that
ratio at typical rendering, not an exact defined conversion. Using the wrong term did not itself cause
the rendering bug above, but conflating "Installer Unit" with "Windows dialog unit" is the same kind of
mixing-up-of-units mistake, and is corrected everywhere the bitmap sizing is described.

Found by comparing `Layouts.cs` directly against WiX's own `WelcomeDlg.wxs`/`InstallDirDlg.wxs` sources
— the `Banner` region diverges from WiX's own convention only on this one field. Every other stock
region (`TitleRow`, `ContentArea`, `BottomLine`, `ButtonRow`) and the Welcome/Exit `DialogBitmap` region
already matched WiX on Y and height; two smaller, pre-existing deltas remain, unrelated to this fix:
`BottomLine`'s Width is **370** (`Layouts.cs`) against WiX's **373**, and `ButtonRow`'s non-rightmost
buttons sit 4 DLU left of WiX's positions on `InstallScopeDlg`/`SetupTypeDlg` (documented in
`InstallScopeDlgBuilder.cs:22` and `SetupTypeDlgBuilder.cs:14` as the phase-6 ButtonRow geometry
deviation) — the rightmost button (Cancel) still lands exactly on WiX's X in every case.
## Fixed: pre-UI registry search conditions no longer crash before the WPF UI exists

`SearchConditionEvaluator.EvaluateRegistryExists`/`EvaluateRegistryComparison` called the bare
`IRegistry.KeyExists`/`GetStringValue` when evaluating a `SearchConditionType.RegistryValue`
condition, instead of their fail-closed `TryKeyExists`/`TryGetStringValue` siblings (added in
beta.6 for exactly this reason — see `IRegistry.TryKeyExists`'s xmldoc). Neither bare call has a
try/catch in `WindowsRegistry`: an author who declares a pre-UI prerequisite with
`SearchConditionType.RegistryValue` against a path the current user cannot read (an ACL-restricted
key such as `HKLM\SECURITY`, a vendor key with tight ACLs, another user's `HKU` hive) got a
`SecurityException` escaping through `PreUIPrerequisiteDetector.IsInstalled` and out of the
NativeAOT bootstrapper before the WPF UI process is even launched — a raw crash with no dialog, not
a graceful "prerequisite not found." Beta.6 fixed the equivalent bare `KeyExists` call in
`BuiltInVariables.PopulateRebootPending` but did not extend the same fix to
`SearchConditionEvaluator`; this release closes that gap.

All three call sites (`RegistryValue` "exists" against a key, "exists" against a value name, and
the version/string comparison branch) now route through `TryKeyExists`/`TryGetStringValue` and
propagate a genuine read failure (access denied / unreadable — not "value absent") as a
`Result<bool>.Failure` instead of letting the exception escape.

**Chosen behavior: fail closed by treating an unreadable registry probe as "condition not
satisfied," the same way beta.6 already fails closed for `RebootPending`.** This is not a new rule
invented for this fix — `PreUIPrerequisiteDetector.IsInstalled` already treated an evaluation
`Failure` the same as `false` before this change (its own comment: "Better to attempt a redundant
install than to silently skip a required prereq"), so propagating the read failure as a genuine
`Result<bool>.Failure` slots into behavior the caller was already designed for.

**The tradeoff is more than a possibly-redundant install.** When an unelevated user hits a missing
pre-UI prerequisite, `PreUIBootstrapOrchestrator` relaunches the process elevated (a UAC prompt),
and the prerequisite installer then runs with that elevation. `PreUIPrerequisiteInstaller.HandleExitCode`
maps any exit code that is not 0, 3010 (soft reboot), or 1641 (forced reboot) to `PreUIResult.Failed`,
which `PreUIBootstrapOrchestrator` turns into `PreUIBootstrapOutcome.ExitFailed`, which
`BootstrapperRunner` turns into a process exit code of 1 — the WPF UI never launches. Redists
routinely return a non-zero exit code when the prerequisite is already present (e.g. "newer version
already installed"), so a redundant install triggered by an unreadable search condition is not
merely wasted work: it can end the whole bootstrap with a UAC prompt and a silent `exit 1`.
Before this branch, a `Failure` from `SearchConditionEvaluator` could only come from an authoring
mistake (an unsupported condition type). After this branch, it can also come from the runtime
environment (an ACL-restricted key at install time) — so this specific failure outcome, which used
to be deterministic given a fixed manifest, is now machine-dependent. This is still the safer of
the two wrong answers compared to silently treating an unreadable key as "prerequisite satisfied"
and skipping installation of something genuinely missing — but it is a real, not hypothetical, cost.

No caller observes a raw exception. **Both callers that consume the `Failure` today discard its
`Error` without logging it** — `PreUIPrerequisiteDetector.IsInstalled` and `PackageDetector.EvaluateAllSearchConditions`
both collapse `result.IsFailure` straight to `false`/"not installed" with no log line, and
`BootstrapperRunner`'s `ExitFailed` case returns 1 with nothing written to stderr. A user who hits
this path sees a UAC prompt, a prerequisite install, and a silent exit — no message anywhere
explains why. This is tracked as a separate follow-up, not fixed in this release.

**`PackageDetector`'s own `SearchConditionEvaluator` instance (used by `DetectStep`, not the pre-UI
path) was not reachable in production as of the paragraph above — since fixed in this same release,
see "Fixed: search-condition package detection never ran in production" below.**

**Not covered by this fix:** `MsiDetector.IsProductInstalled`/`GetInstalledVersion` still calls the
bare `IRegistry.KeyExists`/`GetStringValue` directly (not through `SearchConditionEvaluator`), and
does run on the main managed pipeline (`DetectStep`, after the WPF UI and IPC channel already
exist), which `PipelineRunner` wraps in a top-level catch that turns an unhandled exception into a
`PipelineEvent.Failed` and a graceful shutdown rather than a raw pre-UI crash — a materially
different, lower-severity shape than the one this release fixes. `DotNetDetector`'s shared-framework
probe also still calls the bare `IRegistry` methods, but as of this release it has no construction
site anywhere in `src/` — it is not wired into `DetectStep` or any other pipeline path, so it is
currently unreachable in production rather than merely lower-severity. Both are left open as
separate follow-ups.

## Fixed: search-condition package detection never ran in production, so a REG_DWORD prerequisite fix landed unreachable

The REG_DWORD fix above is correct but was dead code on the only path that matters: `DetectStep`
always built its `PackageDetector` via the one-argument constructor (`new PackageDetector(_registry)`),
which leaves `_searchEvaluator` permanently `null` — `EvaluateAllSearchConditions` returns `false` at
its null guard before an evaluator is ever constructed. Every `DetectionMode.SearchOnly`/`Combined`
package (which is how every chain prerequisite, including `NetFx472()`/`VCRedist14x64()`, is detected)
reported `NotInstalled` regardless of what search conditions said. Every existing search-condition test
constructed `PackageDetector` directly via its two-argument constructor — the one production never
called — so none of them could have caught this.

Two changes were needed, not one:

- `InstallerPipelineBuilder` gained `WithFileSystem(IFileSystemProvider)`; `EngineSession.BindToPipe`
  now calls it with `WindowsFileSystemProvider.Instance` (the same production adapter
  `DefaultPreUIPrerequisiteDetector` already uses pre-UI), and `DetectStep` forwards it into
  `PackageDetector`'s two-argument constructor. This alone was not enough: that constructor built its
  `SearchConditionEvaluator` with the file system but **no registry**
  (`new SearchConditionEvaluator(fileSystem)`), and `EvaluateRegistryValue` returns
  `Failure("Registry provider not available")` whenever its registry is null — so a `RegistryValue`
  condition (every built-in prerequisite's actual detection mechanism) still could not match.
- `PackageDetector`'s two-argument constructor now passes its own `IRegistry` into
  `SearchConditionEvaluator` too (`new SearchConditionEvaluator(fileSystem, registry)`), which is what
  finally makes `RegistryValue` conditions evaluate for real.

A third gap sat behind those two: `Planner.CreatePlan`'s `detectedPackageStates` parameter — the thing
that lets `Planner.OrderWithPrerequisites` skip a prerequisite already detected as installed instead of
scheduling it again — was never passed by `PlanStep`. `PipelineContext` gained
`DetectedPackageStates`, populated by `DetectStep` from the same per-package detection pass it already
ran for UI notifications, and `PlanStep` now forwards it into `CreatePlan`.

**Behavior change worth calling out explicitly:** with all three gaps closed, a `Vital` prerequisite
that search-condition detection finds already installed is now *skipped* at plan time instead of being
reinstalled on every run. For any bundle shipping a search-condition prerequisite (the built-in
`NetFx472()`/`VCRedist14x64()` groups, or an author's own), this is the whole point of the fix — but it
is a real behavior change from every prior release, where detection was silently inert and every such
prerequisite reinstalled unconditionally on every launch.

Regression coverage goes through the actual production construction path
(`InstallerPipelineBuilder` → `DetectStep` → `PackageDetector`) with a `RegistryValue` search condition
against a REG_DWORD value, not a hand-built two-argument `PackageDetector` — the shape every prior test
used, and the shape that proved nothing about whether production ever reached this code.

## Fixed: `BundleBuilder.Build()` generated a fresh random `UpgradeCode`/`BundleId` on every build, so bundle upgrade detection could never match anything

`BundleBuilder.Build()` only derived a deterministic `UpgradeCode`/`BundleId` (via
`GuidUtility.CreateDeterministicGuid`) when `Reproducible()` was configured; otherwise it fell back to
`Guid.NewGuid()`. `UpgradeCode` is the value `RelatedBundleDetector` matches a newly launched bundle
against a previously installed one to detect an upgrade — a fresh random value on every build means no
two builds of the same product ever share an `UpgradeCode`, so upgrade detection can never find a match,
ever. This is worse than the MSI `ProductCode` gap fixed earlier this cycle (issue #61): that one at
least let a first install succeed and only broke the *next* upgrade. This one meant there was never a
"next install" that could recognize the one before it as the same product.

**Both codes are now deterministic by default, unconditionally — not gated on `Reproducible()`** —
matching the shape of `PackageBuilder`'s `UpgradeCode`/`ProductCode` derivation (§9.1, §8.2 in
`documentation.html`):

- **`UpgradeCode`** = deterministic hash of `"bundle::" + Name + Manufacturer`. This identifies the
  bundle across every version and scope, using the same two inputs as
  `PackageBuilder.UpgradeCode`'s derivation (which likewise excludes `Version`, `Architecture`, and
  `Scope`) but under a `"bundle::"` key prefix — without it, a bundle and an MSI sharing the same
  `Name` and `Manufacturer` (the ordinary case: a bundle wrapping an MSI of the same product) would
  derive the identical `UpgradeCode` for two separately-installed, separately-uninstalled artifacts.
- **`BundleId`** = deterministic hash of `"bundle::" + Name + Manufacturer + Version + Scope` (same
  `"bundle::"` prefix, for the same reason). This identifies one specific build, matching
  `ProductCode`'s version-specific role. `Scope` is included because
  `BundleModel` has no `Architecture` field to fold in, but `Scope` changes the installed artifact the
  same way `Architecture`+`Scope` change `ProductCode` (`EngineSession.BindToPipe` resolves a different
  cache root per `InstallScope`) — a `PerMachine` and a `PerUser` build of the same
  `Name`/`Manufacturer`/`Version` must not collide on one `BundleId`.

**Unlike the MSI side, the `Version` string is not normalized before hashing.** `PackageBuilder`
deliberately clamps its key to `Major.Minor.Build` because `PropertyTableProducer` writes
`Version.ToString(3)` into the compiled MSI — a 4th (Revision) component never reaches the package, so
including it in the `ProductCode` key would let a CI-only revision bump mint a new `ProductCode` while
the recorded `ProductVersion` stayed identical. Bundles have no such ceiling: `ManifestGenerator` writes
`BundleModel.Version` into `InstallerManifest` verbatim, with no truncation. So `BundleId` keys on the
raw authored string as-is — `"1.0"`, `"1.0.0"`, and `"1.0.0.100"` are three distinct recorded values and
therefore three distinct `BundleId`s, which is correct rather than a gap: there is nothing to normalize
away, because nothing gets normalized on the way to the manifest either.

**Explicit values still win.** `.BundleId(...)` / `.UpgradeCode(...)` continue to take precedence over
the derived value, unchanged.

**Behavior change: every already-shipped bundle's `UpgradeCode` *and* `BundleId` change on the next
build using this version.** If you have already shipped a FalkForge bundle built before this fix, its
embedded `UpgradeCode` and `BundleId` were random values baked in at that specific build (or, if you
called `Reproducible()`, already the same deterministic values this fix now produces unconditionally —
that case is unaffected). Rebuilding that bundle with this version, without pinning `.UpgradeCode(...)`
and `.BundleId(...)` explicitly, produces **different** values for both than the ones already in the
field. Anyone who wants their next release to be recognized as an upgrade of a bundle shipped before this
fix must call `.UpgradeCode(...)` with the exact GUID recovered from the previously shipped build (the
same "pin the old value" pattern documented for MSI `UpgradeCode` migration in `documentation.html`'s
Concepts chapter, "ProductCode, UpgradeCode & PackageCode" → "The Rule: Reuse the Old UpgradeCode" —
inspect the old bundle's compiled manifest, or a build log/artifact from the original build, to recover
it) rather than letting it re-derive.

**`BundleId` has live consumers, and its version-specific derivation is a trap for update feeds.**
Unlike `UpgradeCode`, `BundleId` is not inert today. `UpdateFeedParser.Parse` rejects a fetched feed with
`UPD003` unless `feed.BundleId` equals the running bundle's own `InstallerManifest.BundleId` (the value
`DetectStep.CheckForUpdateAsync` passes through as `expectedBundleId`); `InstanceLock.TryAcquire` names
the machine-wide install mutex `Global\FalkForge_Install_<BundleId>`; and `CacheLayout.GetBundlePath`
keys the package cache root on it. The update feed case is the sharp edge: a published feed's `bundleId`
is meant to be read as a stable, cross-version product identifier, but the derived `BundleId` changes on
every version bump by design (that's what makes `"1.0.0"` and `"1.0.1"` distinct builds). An author who
configures `.UpdateFeed(...)` on the default derived `BundleId` ships a feed that starts failing
`UPD003` on the very next version bump. **Call `.BundleId(...)` with one fixed GUID before configuring
`.UpdateFeed(...)`** so the identifier the feed checks against stays constant across every version you
publish; this is in addition to, not instead of, pinning `.UpgradeCode(...)` for upgrade-detection
continuity above.

**This does not yet make bundle upgrades work end-to-end.** `RelatedBundleDetector` matches against a
`BundleUpgradeCode` registry value under
`HKLM\SOFTWARE\...\Uninstall\<key>`/`HKCU\SOFTWARE\...\Uninstall\<key>` — but nothing in this codebase
writes that value. No bundle self-registers an Add/Remove Programs entry anywhere in `src/`; the ARP
registration path for bundles (as opposed to the MSI packages a bundle chains) does not exist yet. So
even with a stable `UpgradeCode`, `RelatedBundleDetector` finds nothing to match against on a real
machine today — and `DetectStep` deliberately keeps its results observational only (UI notifications),
never feeding them into `ctx.RelatedBundles`, because `Planner.AddRelatedBundleUninstalls` would
synthesize an `Uninstall` plan action with an empty `SourcePath` that `BundleExecutor` rejects, aborting
the whole apply — related-bundle *uninstall* execution is a separate, unimplemented feature (see the
`IMPORTANT` comment in `DetectStep.cs`). This fix removes the "the GUID can't even be a stable key"
blocker; the "nothing writes the registry value the key would be looked up by" blocker is a distinct,
larger gap tracked separately, not closed here.
