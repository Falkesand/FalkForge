# FalkForge v0.5.0-beta.7 (unreleased)

This file accumulates fixes landed on `main` since `v0.5.0-beta.6` was tagged. It is not yet cut or
published — no version, packaging, or requirements section below, because none of that has been
decided for this cycle yet. Entries are added as work lands; this note will gain the usual sections
(Breaking changes, Packaging, Requirements) when the release is actually cut.

## Fixed: an author-scheduled action colliding with a baseline standard action now fails with a named diagnostic (SEQ001) instead of a bare duplicate-row error

`v0.5.0-beta.6` warned that hand-scheduling `FindRelatedProducts` — the standard workaround for issue
\#65 before that release fixed it — now collides with the compiler's own baseline row, and that the
collision "fails the build at `PrimaryKeyValidator` ... a build-time validation failure, not a silent
no-op." That was true, but the failure was a generic `Duplicate primary key in table
InstallExecuteSequence: FindRelatedProducts`-style message with no guidance pointing at the actual
cause — exactly the audience least likely to guess it, since they are the people who diagnosed issue
\#65 themselves and are now hitting a *new* error from the *fix* for the bug they already worked around.

`InstallExecuteSequenceTableProducer` and `InstallUISequenceTableProducer` now reject a manually
scheduled action whose name collides with a baseline row before any table row is even produced, with
a diagnostic that names the cause:

```
SEQ001: 'FindRelatedProducts' is scheduled automatically by the compiler and collides with the
InstallExecuteSequence baseline row of the same name. Remove the manual ExecuteSequence(...) entry
for 'FindRelatedProducts' — InstallExecuteSequence's primary key is Action, so scheduling it again
would fail the build with a duplicate-row error.
```

The same guard applies to `InstallUISequence`/`UISequence(...)`, and to any standard action name the
sequence producers themselves schedule — not only `FindRelatedProducts` — so scheduling e.g.
`InstallFiles` or `AppSearch` by name is caught the same way. The check is derived from the exact
baseline row set each producer builds for the package being compiled (not a separately maintained
list), so it cannot drift out of sync with what the producer actually emits.

**This does not cover action names contributed by extensions.** Rows an extension's
`IMsiTableContributor` emits directly into `InstallExecuteSequence`/`InstallUISequence` — for example
the ODBC extension's `InstallODBC`/`RemoveODBC` rows — are merged in after the sequence producers have
already run, so they are outside the baseline snapshot SEQ001 checks against. An author whose manually
scheduled action collides with one of those still hits a build failure, just the generic
duplicate-primary-key error, not SEQ001's named diagnostic.

**This does not affect using a baseline action name as a position anchor.** Scheduling a *different*
action `.After("FindRelatedProducts")` or `.Before("FindRelatedProducts")` — as this repository's own
`demo/09-advanced-msi/Program.cs` does for `SetUpgradeFlag` — still works exactly as documented in the
beta.6 notes; SEQ001 only fires when the author-scheduled action's own name collides with a baseline
row, never when a baseline name is merely referenced as a relative position.

**Migration:** if you hit SEQ001, delete the manual `ExecuteSequence(...)`/`UISequence(...)` entry for
the named action — the compiler now schedules it for you. See &sect;8.14 in `documentation.html` and
`docs/validation-error-codes.md` (SEQ001) for the full detail.
